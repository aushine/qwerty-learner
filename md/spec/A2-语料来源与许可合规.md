## 信源置信度说明（务必先读）

本文档的结论分两类，置信度标准不同：

| 结论类型 | 采信标准 | 本文档中的标注 |
|---|---|---|
| **许可证兼容性判定** | 必须以 **FSF / Creative Commons 官方文本或官方 wiki** 为准，不接受博客转述 | 标注「官方依据」并给出判定来源 |
| **开源项目元数据**（star 数、许可、依赖数） | 以 GitHub 仓库页面 / 官方镜像为一手；第三方统计站为二手 | 标注「一手」或「二手，需核对」 |
| **公有领域判定**（作者卒年 → 是否公版） | 卒年需 ≥2 信源一致；**保护期计算规则以《著作权法》条文为准** | 卒年标注置信度；**卒年无法确认者一律标「待官方核对」，禁止推测** |
| **篇目字数** | 字数随版本（繁简、异体、标点、分段）浮动 | **本文档只给「字数区间」，并注明「精确字数须在构建期由脚本统计实际入库版本」** |

**⚠️ 三条硬性纪律**：
1. **卒年查不到或只有一个信源的作者，其作品一律按「仍在版权期」处理**（保守原则），不得因「感觉是老作品」就内置。
2. **凡是「原作已公版但通行的是译本/校注本」的作品，一律按「不可用」处理**，除非能确认所用的具体版本本身也是公版（见 §3.3 译本双层权利）。
3. **本文档不提供任何「打擦边球」的方案**。所有 ❌ 项都是硬红线，不接受「用量很少应该没事」「教育用途应该算合理使用」等论证（见 §4.4 为什么合理使用救不了我们）。

## 一、合规总纲：三条红线 + 一个判定框架

### 1.1 本项目适用的许可证

`qwerty-learner` 采用 **GPL-3.0**。这意味着：

- 本项目**分发**（发布 Web 版是否构成分发存在争议，见 §1.3）时，**整体必须保持 GPL-3.0**；
- 任何并入仓库的**代码、数据、文案**，其许可必须**允许在 GPL-3.0 下再分发**；
- 任何附加了**进一步限制**（非商业、禁止 996、需单独授权、仅限学习研究）的材料，**一律不得并入**。

### 1.2 ⭐ 三条红线（team-lead 已拍板，本文档负责落地论证）

| # | 红线 | 本文档的落地章节 |
|---|---|---|
| **R-1** | **官方码表（小鹤官方键位表 / 各输入法码表文件）仅用于开发期交叉验证，不入库、不进构建产物** | §5.1、§7.4 |
| **R-2** | **内置语料只使用公有领域（公版）文本 + 明确兼容许可的开源数据集** | §2、§3、§5 |
| **R-3** | **近代/在世作品不内置，只走「用户自导入 TXT」路径** | §4、§8 |

### 1.3 Web 应用是否构成「分发」？（必须写进 spec 的前置判断）

GPL-3.0 的传染性义务在**分发（convey）**时触发。纯 SaaS 场景下 GPL-3.0（非 AGPL）不强制开放服务端代码。但本项目情况特殊：

- `qwerty-learner` 是**纯前端应用**，构建产物（JS/CSS/JSON）**完整下发到用户浏览器**，用户可完整获取 → **实质上构成分发**；
- 语料 JSON 会**打包进前端产物**，用户可直接下载 → **语料数据必然被分发**。

> **⭐ 结论**：**不要指望「我们只是网站、不算分发」的抗辩**。所有并入语料的数据都必须满足 GPL-3.0 兼容要求。这是本文档全部判定的前提。
> 附带收益：既然语料必然公开，**选择公版语料就没有任何「数据泄露/被爬」的额外损失**，红线 R-2 不带来商业上的劣势。

### 2.1b `L6-EX`（公文/法律文书）—— ⭐ 合规上最安全的一类语料

`01` CN-D9 定义了 **L6-EX：公文/法律文书 ≥20 篇，须标注来源与版权状态，不得直接搬运真实未公开文书，需含法律术语、法条序号（如「第一百零七条」）、生僻字**。

**⭐ 本文档的合规判定：这是全部层级中许可风险最低的一级。**

| 数据类型 | 许可依据 | GPL-3.0 兼容结论 | 我方动作 |
|---|---|---|---|
| **法律、行政法规、地方性法规、规章** | ⭐ **《著作权法》第五条第一项：「法律、法规，国家机关的决议、决定、命令和其他具有立法、行政、司法性质的文件，及其官方正式译文」不适用本法保护** | ✅ **完全可用，无需授权、无需署名义务（但建议标注法规名与条款号）** | 从**国家法律法规数据库 `flk.npc.gov.cn`**（全国人大常委会官方）取现行有效文本 |

### 2.1c `L7`（标点/数字/中英混输专项）—— 无著作权问题，但有字符集工程约束

`01` CN-D10 定义了 **L7：全角逗号/句号/顿号/冒号/分号/引号/书名号/括号/破折号/省略号/间隔号 + 数字全半角 + 中英混输**（示例：`我的微信号是Tom_123，请查看2025年Q1报表`）。

| 维度 | 判定 |
|---|---|
| **著作权** | ✅ **无任何问题**。**标点符号、数字、通用格式属「历法、通用数表、通用表格和公式」类事实性内容**（《著作权法》第五条），**语料本身由我方原创撰写** |
| **数据来源** | ✅ **无需外部数据源**：我方自行撰写 20~50 条职场/生活场景的中英混输句子即可（原创 → GPL-3.0） |
| **⚠️ 工程约束（本文档提示，非许可问题）** | ⭐ L7 需要判定**全角标点、数字、Shift 组合键、中英切换**，字符集远超对码轨的 `KeyA`~`KeyZ` + `Semicolon`。<br>→ **✅ 已由 X-A2-2 裁定收口**：L7 恒走独立的 `ime` 轨（`02` §5 已如此定义），**不复用双拼对码轨的字符集限制，也不需要与方案层做任何互斥开关**（理由见下行）。<br>→ `01` CN-D10 已要求「全角/半角不匹配判错并单独归类『标点格式错误』，不与错字混算」——**这意味着 L7 需要一套独立的错误分类维度，需在 `05`（数析）的指标模型中体现。** |
| **✅ 与 A1 §5.2 的 `Semicolon`「冲突」—— 已由 X-A2-2 裁定为不成立（无需互斥）** | **初稿的担忧**：微软双拼用 `;` 键承载 `ing` 韵母（A1 §4.5），而 L7 要判定「半角分号 vs 全角分号」，两者在 `event.code` 层面都是 `Semicolon`，无法区分全角/半角。<br>**📌 裁定结论（主理人 2026-10-17，X-A2-2）：不需要「方案层与 L7 做互斥」，两者天然隔离。**<br>**理由**：① **`ing` 只存在于对码轨的「编码校验语义」**——它校验的是「用户是否按对了两个物理键」，与上屏字符长什么样无关；② **L7 恒走 ime 实战轨**，判定的是「上屏字符是否与目标文本一致」，此时编码已被输入法内部消化，**方案层根本不参与**；③ 因此**同一个 `Semicolon` 物理键不会同时出现在两轨的判定逻辑里**，不存在需要仲裁的冲突。<br>**→ 职责边界一句话（已写入 A1 §1.2 与 §5.2.1）：方案层只管编码映射，不管字符形态判定。**<br>**→ 实施纪律两条**：① 方案层配置与代码**禁止**出现全角/半角、繁简、异体字相关的任何字段或分支（若发现需要，说明职责划分错了，应退回实战轨处理）；② 实战轨判定器**禁止**反查方案层的 `keyMap`，它只比对 `compositionend` 的 `e.data` 与目标字符串。<br>**→ 剩余的真实工程事项（不属冲突，属实现要求）**：双轨的输入捕获策略差异（对码轨取 `event.code`、实战轨取 `compositionend` 的 `e.data`）需在 `03-模块与架构设计.md` 中明确。**此事项已上报主理人，由主理人统一分派**（本文档不直接联系其他成员）。 |

### 3.2 ⭐ 本项目的公版分水岭：**1975-12-31**

**判定公式**（以本文档日期 2026-10-17 为基准）：

```
作者卒年 ≤ 1975  →  卒后第 50 年 = 卒年+50 ≤ 2025  →  已于 2025-12-31（或更早）届满  →  ✅ 2026 年起公版
作者卒年 = 1976  →  卒后第 50 年 = 2026  →  截止于 2026-12-31  →  ⚠️ 当下（2026-10-17）尚未届满
作者卒年 ≥ 1977  →  ❌ 仍在保护期
```

### 3.3 ⭐ 译本的双层权利（最容易踩的坑）

**规则**：**翻译作品是独立的演绎作品，享有独立的著作权。** 利用译本需**同时**满足两层：
1. **原作**是否在公有领域；
2. **译者**是否已去世满 50 年（即译者卒年 ≤ 1975）。

**只有两层都通过，译本才可用。** 这一条是本项目最大的隐性风险，因为**外国文学作品的中文练习语料几乎全是译本**。

**⭐ 真实判例（强力论据，建议写进 spec 的风险章节）**：
- 叶芝（W. B. Yeats，1865-1939）的 *When You Are Old* **原作早已公版**；

### 3.5 ⭐ L5（诗句）公版篇目候选清单（30 条，含字数区间）

> **⚠️ 清单性质说明**：`01` CN-D7 的验收标准为 **L5 ≥100 首公版诗词**。本清单是 **30 条「精选候选 + 合规举证范式」**，用于首发 PoC 与确立溯源档案的标准写法；**补足到 100+ 首的路径见 §2.1 表格后的「数量缺口提醒」与 §9 Q-19**（可从 chinese-poetry 的 37 万篇中用本节的五条标准自动化批量筛选，瓶颈在人工抽检工时而非数据可得性）。
> **⚠️ 与 `02` §5 的 `inputMode` 对齐**：L5 在 `02` §5 中定义为 **`inputMode='ime'`（整句上屏）、按句分行逐句输入、隐藏键位图、注音可选（默认关）**，且 `02` §5.1 明确「**情绪价值 > 训练价值，UI 入口建议前置到 S2 阶段**」。→ **本文档的篇目筛选标准应据此调整权重：优先「押韵、朗朗上口、用户熟悉度高」的篇目（`02` §5.1 引社区经验原文：「推荐先打打古诗词，因为很多诗词都押韵，打起来比较爽快」），而非优先「键位覆盖全面」的篇目。** 下文「练习价值」列中偏向键位训练的备注（如 #9「zh/ch/sh 声母密集」）应视为**次要价值**。
> **⚠️ 字数与 `02` 的分句约束**：`02` §5 规定 L5 **按句分行、逐句输入**，因此**单句字数（而非全篇字数）才是交互体验的决定变量**。下表「字数区间」为**全篇正文汉字数**；五言绝句单句 5 字、七言绝句单句 7 字、词的单句 3~9 字不等 —— **全部落在舒适区内，无需额外切分**。

1. **作者卒年 ≤ 1975**（绝大多数为唐宋明清，天然公版）；

4. **多音字可控**：**多音字不是排除项**，但需在构建期用 `pinyin-pro` 的上下文消歧并**人工抽检**（见 §7.3）；

### 3.6.1 ⭐ codeComplexity 估值（X-A2-1 裁定的新增要求，实测产出）

> **裁定口径（必须遵守）**：
> 1. **`level` 只定文体类型 / 展示分组**（L6-a = 文言短篇、L6-b = 标准文章，用于 UI 归类与用户预期管理）；
> 2. **实际出题顺序由 `codeComplexity` 主导**（不随字数单调递增）；
> 3. `codeComplexity` 按 `05` §6.6 已裁定的 **C1~C6** 计算，**词条级取 max**（一个词的所有音节取最高复杂度等级）。

**C1~C6 判定口径（依 `05` §6.6 + A1 官方取证键位表）**：

| 码 | 含义 | 判定条件（本文档实测所用） | 小鹤键位 |
|---|---|---|---|
| **C1** | 单韵母 | 韵母 ∈ {a, o, e, i, u, ü} | A/O/E/I/U/V（与全拼同位，零学习成本） |
| **C2** | 复韵母 | 韵母 ∈ {ai, ei, ao, ou, ia, ie, iao, iu, ui, uo, ua, üe, er, uai} | D/W/C/Z/M/P/N… |
| **C3** | 鼻韵母 | 韵母 ∈ {an, en, ang, eng, ing, ong, ian, in, iang, uang, un, iong, ün, uan} | J/F/H/G/K/S/L/R… |
| **C4** | 特殊键 | 声母 ∈ {zh, ch, sh} | V/I/U |
| **C5** | 零声母 | 音节以 a/o/e 开头（无声母） | 见 A1 §3.2（α/β 双口径） |
| **C6** | 易混韵母对 | 韵母 ∈ 六对易混：iang↔uang、in↔ing、en↔eng、an↔ang、ie↔ei、iu↔ui | 跨键 |

#### 3.6.1.1 🔴 实证发现（必须上报主理人裁定，编号 X-A2-3）：**篇目级取 max 会完全饱和，「词条级取 max」需明确聚合口径**

本文档用 `pypinyin` 对 **12 篇代表篇目全文**做了实测（脚本可复现，音节级判定按上表规则）。**发现裁定要求的「词条级取 max」若直接聚合到篇目级，会得到零区分度的结果：**

**【实测表一】篇目级 max —— ❌ 12/12 全部饱和为 C6，无任何区分度**

| 篇目 | 音节数 | 篇目级 max |
|---|---|---|
| 陋室铭 / 记承天寺夜游 / 诫子书 / 爱莲说 / 马说 / 小石潭记 | 47~86 | **C6** |
| 桃花源记 / 岳阳楼记 / 醉翁亭记（节选） | 91~108 | **C6** |
| 匆匆 / 背影 / 少年中国说（节选，白话） | 70~97 | **C6** |

> **原因（结构性，非计算错误）**：任何一篇 ≥47 字的中文文章，**必然**同时包含至少一个 `in`/`ing`、`an`/`ang` 或 `iang`/`uang` 成员（C6 易混对覆盖了最常用的鼻韵母），因此**篇目级取 max 恒等于 C6**。**这不是 L6 特有的问题——L1~L5 同样会饱和。**
> → **结论：「取 max」只能用于词条级（用于给单个词打标、驱动错键归因与专项出题），绝不能直接聚合为篇目级难度分。**

**【实测表二】改用「C 分布占比 + 加权分」后 —— ✅ 区分度显著（1.84 分跨度）**

#### 3.6.1.2 ⭐ 三条对出题顺序有直接影响的实测结论

1. **✅ 「字数 ≠ 难度」已被数据证实，裁定口径完全正确且必要**：

| 2 | 灵 | **líng** | ing | ✅ | C3 + **C6** |
| 3 | **馨** | **xīn** | **in** | ❌ **不是 ing** | C3 + **C6**（in↔ing 易混对） |
| 4 | 青 | **qīng** | ing | ✅ | C3 + **C6** |
| 5 | 丁 | **dīng** | ing | ✅ | C3 + **C6** |
| 6 | 经 | **jīng** | ing | ✅ | C3 + **C6** |
| 7 | 形 | **xíng** | ing | ✅ | C3 + **C6** |
| 8 | 亭 | **tíng** | ing | ✅ | C3 + **C6** |
| 9 | 有 | yǒu | ou | ❌ | C2 |

**实测结论（三条，其中第 1 条是修正）：**

1. **⚠️ 修正：「馨」的拼音是 `xīn`（韵母 `in`），不是 `ing`。** 因此 ing 韵脚是 **7 个而非 8 个**（名/灵/青/丁/经/形/亭），占 9 个韵脚的 **78%**。
   → **但这个「错误」反而让素材价值更高（见结论 2）**。原线索把「馨」归入 ing，属常见误读——**《陋室铭》押的是中古「青韵」，普通话中 `in` 与 `ing` 已分化，「馨(xīn)」与「名(míng)」今音不同韵母但仍同属一个韵部**。**用户自己也会犯这个错**，因此这是极佳的教学切入点。

2. **⭐ 素材价值升级：《陋室铭》不只是「C3 鼻韵母素材」，更是「C6 易混对 in↔ing 的天然教学素材」**。
   - **7 个 `ing` 韵脚 + 1 个 `in` 韵脚（馨）混排在同一韵文中**，用户在朗读/背诵记忆中会自然把「馨」读成后鼻音；
   - 在小鹤双拼中，**`in` → `B` 键、`ing` → `K` 键**（A1 §2.2 L83/L70），**两键相距甚远**，一旦前后鼻音判断错误，**手指要跨半个键盘**，错误代价极高且极易被察觉；
   - → **这是「语料 × 机制耦合」的完美案例**：不需要人为编造练习题，**一篇 81 字的公版名篇自带 in/ing 混淆训练场**。
   - **产品用法建议（交 `09` §7 作为耦合案例二）**：① 把《陋室铭》设为 **C6 易混对专项关**；② 在题面为「馨」标注拼音 `xīn`（呼应 A1 §3.3 C-5 的「题面必须明示拼音」实施要求，同理适用于前后鼻音）；③ 错键热力图上若用户在 `B`/`K` 两键间高频混淆，**自动推荐本篇作为矫正素材**（对应 `05` §6.6「C6 由 LN5 混淆矩阵数据驱动动态生成」）。

3. **⭐ 全篇 ing/eng 音节占比仅 8.6%（7/81），但韵脚位置占比 78%**——**这个反差本身就是产品机会**：
   - 若按「全篇占比」选素材，会低估《陋室铭》的专项价值；
   - 若按「韵脚位置占比」选素材，**韵文类（铭/诗/词）天然优于散文类**，因为韵脚是用户最有记忆锚点的位置；
   - → **建议 `04` 在语料元数据中增加「韵脚位置标记」**，使专项出题可以只抽韵脚句（如《陋室铭》只练「有仙则名 / 有龙则灵 / 入帘青 / 无白丁 / 阅金经 / 之劳形 / 子云亭」7 句），**用 40 字的量达到 81 字的专项训练效果**。此建议已同步给 `09` 作为「韵脚接龙」玩法的语料基础。

> **⚠️ 数据可信度**：以上韵脚实测基于 `pypinyin` 默认读音 + 本文档采用的通行简体版本。**「馨」的 `xīn` 读音在《现代汉语词典》中唯一，无多音字风险，结论稳定。** 但**其他文言文韵脚判定需注意多音字**（如《岳阳楼记》「浩浩汤汤」的「汤」应读 shāng），呼应 §3.6.1.3 的多音字风险声明。

### 4.4 ❌ 为什么「合理使用 / 教育用途」救不了我们（必须写进 spec）

**常见错误论证**：「我们是开源教育项目、非商业、每篇只用几十个字、还标了作者，应该算合理使用。」

**为什么这个论证站不住**：
1. **中国《著作权法》第二十四条的「合理使用」是封闭式列举**，其中与教育相关的是「**为学校课堂教学或者科学研究**，翻译、改编、汇编、播放或者少量复制已经发表的作品，**供教学或者科研人员使用**，但不得出版发行」。我们的用户是**不特定的社会公众**，不是「教学或科研人员」，**不满足主体要件**；且 Web 公开发布接近「出版发行」。
2. **第二十四条另有「为介绍、评论某一作品或者说明某一问题，在作品中适当引用」** —— 打字练习是**把作品当作练习素材整体使用**，不是「为评论而引用」，**不满足目的要件**；且引用整首诗/整段文章难谓「适当」。
3. **维基文库的版权方针明确否决了这条路**（一手原文）：「**合理使用要求按需引用原文，而我们的要求是将原文整体引用，因此，請勿宣稱合理使用刊登他人有版權的整篇作品。在通常情况下，合理使用在这里不适用。**」并援引美国判例 *Harper & Row v. Nation Enterprises* (1985)：从福特总统回忆录中引用不到 400 字仍被判侵权，因为那几段构成了「作品的心脏」。
4. **本项目是公开可访问的 Web 应用，语料会完整下发到用户浏览器**（§1.3），**不存在「小范围使用」的事实基础**。

> **⭐ 结论写进 spec**：**Non-goals 中明确一条：「不依赖合理使用抗辩。任何内置语料必须可自证为公有领域或兼容许可，举证材料留档于 `docs/corpus-provenance/`。」**

### 6.3 ⭐ 为什么 Anti-996 与 GPL-3.0 不兼容（红线论证）

**Anti-996 License 的核心条款**：要求被许可人**不得违反劳动法律标准**（包括但不限于工时、加班补偿、劳动安全），并允许在违反时**终止许可**。

**不兼容的三条理由**：

1. **GPL-3.0 §7「进一步限制」禁止条款**：GPL-3.0 第七条明确规定，分发者**不得对被许可人行使 GPL 授予的权利施加任何进一步限制**（"You may not impose any further restrictions on the exercise of the rights granted or affirmed under this License"）。Anti-996 的「合规使用劳动法」条件**正是一项进一步限制**——它把 GPL 授予的无条件自由，变成了**有条件的自由**。
2. **不是自由软件许可**：Anti-996 **未通过 OSI 认证**，**不在 FSF 的许可兼容列表中**，**GitHub 官方 license 列表不收录**。它属于「source-available」而非「open source」。
3. **双许可不改变结论**：纸砚采用 **MIT + Anti-996 双许可**。理论上双许可意味着使用者可**任选其一**（若确实如此，选 MIT 则无问题）。**但存在两个不确定性**：
   - ⚠️ 其 LICENSE 文件的**实际写法**是否为标准双许可（"licensed under MIT OR Anti-996"），还是**叠加式**（"licensed under MIT AND Anti-996"，此时 Anti-996 的附加限制仍然生效）；
   - ⚠️ 即使可任选 MIT，**该项目的数据文件是否单独声明了 Anti-996**（数据与代码可能适用不同许可）。

> **⭐ 结论（保守原则）**：**在未能实际读取纸砚 LICENSE 文件原文并确认其为「OR」式双许可之前，一律按「不兼容」处理，其代码与数据不复制。** 这条保守原则的成本极低（我方本来就要自行编码整理映射表，见 §6.2），但可完全消除风险。
> **⚠️ 待官方核对（Q-13）**：读取 `Yidadaa/shuangpin` 仓库的 LICENSE 文件原文，确认双许可的连接词是 OR 还是 AND。**即便如此，A1 已决定只借鉴格式思想，此项不影响进度。**

### 7.3 ⭐ 多音字与变调：拼音标注的三大难点（构建期必须处理）

| 难点 | 示例 | 处置建议 |
|---|---|---|
| **多音字按义定音** | 「鹿柴」的**柴 = zhài**（非 chái）；「远上寒山石径**斜**」今音 xié / 古音 xiá；「鬓毛**衰**」今音 shuāi / 古音 cuī | ① 用 `pinyin-pro` 的上下文消歧作基线；② **人工建立读音覆盖表**；③ ⭐ **古音问题统一按今音处理**（§5.2 P-5 决策建议），但可在 UI 提供「古音注记」开关 |

| **儿化音** | 「花儿」「玩儿」 | 打字练习语料**避免选用含儿化音的篇目**（会造成音节切分歧义），或按不儿化标注 |

## 八、用户自导入 TXT 的合规边界（红线 R-3 的落地）

### 8.1 为什么需要这条路径

- **L4 句子 / L6 现代文章**的内置语料受公版限制极大（§4.1 一长串 ❌），**用户的真实需求（练自己爱读的文字、练工作中的常用表达、练某本在版权期的书）无法通过内置语料满足**；
- **这是合规压力最小的解法**：**用户在自己设备上、为自己使用而导入的文本，属于个人使用行为**，我方**不分发**该内容，**不承担分发者的著作权义务**。

### 8.2 ⭐ 三条边界（必须严格遵守，否则避风港失效）

| # | 边界 | 具体要求 |
|---|---|---|
| **B-1** | **纯本地处理，不上传** | 导入的 TXT **只在浏览器本地解析与存储（IndexedDB / localStorage）**，**绝不上传到任何服务器**。这既是合规要求，也是隐私承诺（可作为传播卖点：「你的文字只属于你」） |
| **B-2** | **不提供任何侵权内容的获取渠道** | ❌ **不得内置「热门书籍/网文下载链接」**；❌ **不得内置书名词库供搜索**；❌ **不得与任何资源站做跳转联动**；❌ **不得在文档/营销中出现「可以导入《XX》练习」这类以在版权期作品为示例的宣传** |
| **B-3** | **明示责任归属 + 首次使用确认** | 导入入口需有明确提示：「**请确保您导入的文本用于个人学习目的。导入内容的著作权责任由使用者自行承担，本项目不分发、不存储任何用户上传内容。**」建议**首次导入时弹一次确认**（一次性，可记住选择） |

### 8.3 加分设计（把合规约束变成产品优势）

- **剪贴板导入**（比文件导入更轻，覆盖「看到一段好文字就想练」的场景）；
- **导入时自动检测并提示**：字数、生僻字比例、多音字数量、是否含非常用字符 → 帮用户判断该文本的练习适配度；
- **导入文本的自动分级建议**（按字数/句长/字频给出「适合 L4 还是 L6」的建议）；
- **⭐ 隐私即卖点**：明确宣传「纯本地、零上传、无账号」，这在当下 AI 产品普遍上传数据的环境中是**差异化信任资产**（可与 `09-游戏化与激励设计.md` 的传播钩子呼应）。

## 十、本文档的核心结论（10 条，✅ 2026-10-17 按 X-A2-1/X-A2-2 裁定与实测更新）

2. **⭐ 公版分水岭是「作者卒年 ≤ 1975-12-31」**（依《著作权法》第二十三条：作者终生 + 卒后 50 年，截止于第 50 年的 12 月 31 日）。**据此，毛泽东诗词（卒 1976-09-09）保护期至 2026-12-31，本期不内置，标记为「2027-Q1 可评估」**；穆旦（卒 1977）、郭沫若（卒 1978）同属临界项，2028/2029 起才公版。**同时，署名权与保护作品完整权永久有效 —— 公版作品仍必须署名、不得歪曲篡改。**

3. **⚠️ 修正 team-lead 原判定：徐志摩（卒 1931）与戴望舒（卒 1950）的作品已进入公有领域，应从「反面教材」移入 ✅ 可用清单**（《再别康桥》《沙扬娜拉》《雨巷》均为 L5/L6 极佳素材）。海子（卒 1989）、穆旦（卒 1977）确实禁止。**另一批极易误判的项**：叶圣陶（卒 **1988**，非「民国作家就公版」）、沈从文（卒 1988）、老舍（卒 1966 → **2016-12-31 已届满，✅ 可用**）、丰子恺（卒 1975-09-15 → **2025-12-31 刚届满，✅ 可用，是 2026 年的稀缺新素材**）。

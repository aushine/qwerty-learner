> ### 🔴 v1.3 变更说明（修正一处实现级缺陷 —— 由数析 `05` v3 反向查出）
>
> **缺陷**：v1.2 写「`codeComplexity` 词条级取 `max`」+ CI 断言 `codeComplexity === max(该词条所有字的 C 档)`。**这句话在实现上会被读成「比较 C 档编号大小」，是错的。**
>
> **根因**：`C1~C6` 的**编号顺序 ≠ 教学顺序**。`05` §6.6 的真实教学顺序是 **`TEACHING_ORDER = ['C1','C4','C2','C3','C5','C6']`** —— **C4（特殊声母 zh/ch/sh）排第 2**，因为它只有 3 个键却是双拼与全拼的首要差异点，小鹤官方「一小时记键位」的主体就是它。
>
> **实测错误率（数析抽验 5 种码元组合，2 种判错 = 40%）**：
>
> | 词条含码元 | ❌ 数字 max | ✅ 教学序 max | 后果 |
> |---|---|---|---|
> | C1 + C4 | C4 | C4 | ✅ 一致 —— 🔴 **裁定原文与析客 v1.2 举的正是此例，恰好掩盖了问题** |
> | C5 + C1 | C5 | C5 | ✅ 一致 —— **析客的第二个示例也恰好一致，双重掩盖** |
> | **C3 + C4** | **C4** ❌ | **C3** ✅ | 数字 max 判 C4，但用户**早学过 C4、还没学 C3** → 该词被误判「可出题」，用户撞上真正的卡点 C3 |
> | **C2 + C4** | **C4** ❌ | **C2** ✅ | 同上反向 |
>
> 🔴 **后果性质与裁定 B-3 想避免的完全相同**——「词条过早进入出题池」。即 **v1.2 的 `max` 规则只解决了「平均会低估」，却没解决「编号序 ≠ 教学序」，仍会以 40% 的概率犯同一个错。**
>
> | 修正点 | 落点 |
> |---|---|
> | `max` 规则改为「**教学序 max**」，明确禁止编号数字比较，给出 `TEACHING_ORDER.indexOf` 实现代码 | **§2.13**（新增 v1.3 重大更正块） |
> | 🆕 **新增落库字段 `complexityRank: number`（0~5）= `TEACHING_ORDER.indexOf(codeComplexity)`，构建期必填** —— 让排序方有一个天然有序、无歧义的数值字段可用，杜绝「用字符串比较 C 档」的 bug | **§3.2 / §3.3 / §3.4 全部 JSON 示例 / Step 10.5** |
> | **CI 断言 Q-16 按数析建议增补**：断言 `codeComplexity` == 所含码元在 `TEACHING_ORDER` 中 index 最大者 + 断言 `complexityRank === TEACHING_ORDER.indexOf(codeComplexity)` + 长文取全篇教学序 max | **§8.2 Q-16** |
> | `TEACHING_ORDER` **唯一真源声明为 `05` §6.2/§6.6**，本文档与 `02` **只引用、不另行定义** | **§2.0 G-3 块 / §2.13 / §3.2** |
> | TL;DR 构建期新增字段由 6 个更正为 **8 个**（补 `complexityRank` / `unitCharCount`） | **TL;DR** |
> | §14.1 新增 **X-20**（记录本缺陷与修正）；**X-12** 的「词条取 max」表述已限定为「教学序 max」 | **§14.1** |
>
> 📝 **析客的复盘（已记入 `00` 假设 A-14）**：这处缺陷能藏住，是因为**我举的两个示例（C1+C4、C5+C1）在两种读法下结论恰好相同**。教训是：**规格文档里的示例必须刻意选取「能区分两种候选实现」的反例**，否则示例会给人「规则已明确」的错觉。**数析的穷举式抽验（5 种组合）比举例式验证可靠得多。**

## 📌 TL;DR

中文练习**不使用原有语言学习的词库模式**（「一章 20 个外语单词 + 释义」），而是构建**按认知负荷递进的语料体系（v1.2：12 档 `level`）**：L0 声韵母（全拼专用）→ **L0' 韵母分组（双拼独有，核心差异点）** → L1 高频单字（500/1000/3500 三档）→ L2 双字词组（≥1000）→ L3 四字成语（≥500）→ L4 短句（≥200）→ L5 古诗词（≥100 首）→ 🆕 **L6a 文言短篇（≥12 篇 80-300 字，裁定 G-3）** → **L6b 文章（≥30 篇 300-1500 字）** → L6EX 公文法律（≥20 篇）→ L7 标点数字中英混输专项，另增补 L4C「日常聊天短句层」。

**渐进难度 = 认知负荷递进，而不是字数递增。** 语料必须「真实」——练 `uang` 用「黄/光/王/双」，**不是 `aaaa uuuu` 式无意义重复**。🔴 **裁定 G-3 的关键口径：`level` 只定「文体类型/展示分组」，实际出题顺序由 `codeComplexity`（C1~C6）主导**——《陋室铭》81 字（L6a）的 `codeComplexity` 可能高于部分 L6b 白话散文，**不能假设「L6a 比 L6b 简单」**。

数据结构范式沿用已被验证两次的同构抽象：**`name` = 用户实际敲的键序列（编码，构建期生成）｜`notation` = 展示用汉字（ruby 注音）｜`split` = 拆分提示｜`pronunciation` = 喂 TTS 的同音常用字｜`chapterId` = 自定义章节归属**。这与日语 romaji 词典（`name`=罗马音、`notation`=假名）**完全同构**，是同一条数据抽象的**第三次复用**——山人码 fork 已实证校验引擎、DB、WPM 公式一行未动。🆕 **v1.2/v1.3 按裁定 A/B/G-2 新增 8 个构建期字段：`unitId`（唯一主键）/ `idealCodeLen`（纯编码键数）/ `freqTier`（S/A/B/C）/ `codeType`（编码类型 3 值）/ `codeComplexity`（教学难度 C1~C6，取**教学序** max）/ `complexityRank`（0~5 数值教学序，供排序直接比大小）/ `acceptedCodes`（多口径收敛，`[0]` 为主口径）/ `unitCharCount`（字均归一分母）。**

**贡献门槛最低化 = 贡献者只写汉字。** 编码、注音、多音字消歧、校验报告全部由构建期管线（`scripts/buildChineseDict.*`）自动生成，**运行时零拼音库依赖**，可在 CI 中对 PR 自动评论校验结果。质量靠**四层验证 + Q-1~Q-23 断言**（405 音节全量回归单测 + 官方码表交叉验证 ≥99.6% + 端到端 + 零声母双口径），**不靠肉眼核对**——「双拼练习器最容易出错的地方是键位表写错，而写错了用户会跟着练错」。🔴 **裁定 B-2 合规红线（CR-8）：`freqTier` 的字频只能由我方在公版语料上自行统计，禁止引入任何第三方词频表（BCC 许可不明、SUBTLEX-CH 属 CC BY-NC 与 GPL-3.0 §7 冲突）。**

## 1. 设计原则

### 1.1 为什么不用原先语言学习的词库模式

| 维度 | 原有语言学习词库模式 | 中文输入法练习的需求 | 冲突点 |
|---|---|---|---|
| **单元** | 「一个外语单词 + 释义」 | 「一个汉字/词/句 + 它的编码 + 它的读音」 | 中文需要**三个维度**（形/音/码），原有 schema 只有两个（`name`/`trans`） |
| **`name` 语义** | 要打的**目标文本本身**（如 `abandon`） | 对码轨下 `name` 必须是**用户实际敲的键序列（编码）**，而目标汉字要放在 `notation` | 🔴 语义反转。但这**恰好与日语 romaji 词典同构**（`name`=罗马音、`notation`=假名），F6 已实证 |
| **章节长度** | **硬编码 20 词/章**（`CHAPTER_LENGTH = 20`，F9 / `src/constants/index.ts:3`） | 单字课表每章 **10 字**（小鹤官方「分成 10 字一组来练，击键每秒过 6 换组」）；长文一篇 **1500 字一章**；模考**无章节** | 🔴 必须改造为词条级 `chapterId` + 词典级 `chapterName[]`/`chapterNum[]`（D5 / CN-J3） |
| **难度递进** | 按词频/考试范围分册（CET4 → CET6 → 考研） | 按**认知负荷**递进（韵母 → 字 → 词 → 成语 → 句 → 诗 → 文） | 🟡 原有的「分册」概念可复用，但分级依据完全不同 |
| **判定轨道** | 单一（逐字符） | **双轨**（对码 / 上屏），不同层级用不同轨道 | 🔴 需词典级 `inputMode` 字段（D1 / `03` #1） |
| **多音字** | 不存在（外语无此问题） | **数据质量生死线**（「银行」必须标 `háng` 而非 `xíng`） | 🔴 需构建期词组级消歧（CN-B5） |
| **朗读** | `name` 直接喂 TTS | 生僻字/多音字喂 TTS 会读错 → 需 `pronunciation` 字段喂**同音常用字** | 🟡 山人码 fork 的巧思，直接采纳 |

> **结论**：不是「不用原有词库机制」，而是**在原有机制上扩展 4 个字段 + 改造章节机制**。原有 380 个词典**零改动、零影响**（`inputMode` 可选 + 缺省 `code-match`，`03` §5.1）。

### 1.2 五条核心设计原则

| # | 原则 | 具体含义 | 反面（禁止） |
|---|---|---|---|
| **CP-1** | **渐进难度 = 认知负荷递进，而不是字数递增** | L0'→L7 的每一级递进，都对应一个**新的认知负荷维度**：韵母键位记忆 → 单字整码 → 词组连续两击节奏 → 成语中途不停 → 句读节奏 → 诗的韵律与换行 → 长文耐力 → 公文术语与生僻字 → 标点全半角与中英混排 | ❌ 「L1 = 1 字、L2 = 2 字、L3 = 3 字、L4 = 4 字」这种纯字数递增的分级（那只是把同一难度切成不同长度） |
| **CP-2** | **语料必须「真实」** | 练 `uang` 用「黄 / 光 / 王 / 双」；练 `ing` 用「平 / 明 / 京 / 行」。**每个韵母配 ≥3 个真实例字，每组配 ≥20 个真实字词** | ❌ `aaaa uuuu` 式无意义重复串（CI 需断言：任一词条的 `notation` 不得为同一字符重复 ≥3 次） |
| **CP-3** | **贡献门槛最低化 = 贡献者只写汉字** | 编码、注音、多音字消歧、章节归属、校验报告全部由构建脚本生成。**支持无需本地开发环境的 GitHub Web 界面 PR**（对齐 monkeytype `CONTRIBUTING_BASIC.md`） | ❌ 要求贡献者自己算双拼编码、自己标拼音、自己处理多音字 |
| **CP-4** | **方案表与语料解耦** | 同一份源语料 → 构建期按 5 套方案分别生成编码 → **「支持新方案」= 加一份方案表 + 重跑构建脚本，不改代码** | ❌ 把编码写死在语料文件里（那样每加一个方案就要重做全部语料） |
| **CP-5** | **正确性不靠肉眼核对，靠三层验证** | 405 音节全量回归单测 + 官方码表交叉验证（基准 ≥99.6%）+ 端到端。**「双拼练习器最容易出错的地方是键位表写错，而写错了用户会跟着练错」** | ❌ 「我核对过了，应该没问题」 |

### 1.3 与「只做音码」边界的一致性（I2）

**边界定义**：定长 2 键 + 不需要拆字知识 + 不需要「提笔不忘字」。

**对语料设计的约束**：
- ✅ 全部语料只需「汉字 → 拼音 → 2 键编码」，**不需要字根拆分数据**
- ✅ `split` 字段只填**声韵拆分**（如 `zh + ong`），**不填字根拆分**（如「中 = 口 + 丨」）
- ❌ **不建拆字库**（V1 架构留口但不做，D4 / NG-6）
- ❌ 不收录需要「提笔忘字」训练的字形类内容

> ### 🔴 裁定 G-3 的附加口径：`level` ≠ 难度（**这条比拆分本身更重要**）
> **`level` 只定「文体类型 / 展示分组」，实际出题顺序由 `codeComplexity`（C1~C6）主导。**
>
> 反例：《陋室铭》只有 **81 字**（L6-a），但含大量**文言虚词与生僻码元**，其 `codeComplexity` 很可能**高于**部分 L6-b 的白话散文篇章。**因此绝不能假设「L6-a 比 L6-b 简单」而把它排在前面。**
>
> **同理适用于 L6-EX**：公文虽属「专业扩展」，但其中「的/了/是」类高频虚词密度可能低于日常散文，`codeComplexity` 未必更高。
>
> **落地要求**：
> - **构建期**：每篇长文需按 §2.13 的规则计算全篇的 `codeComplexity` 聚合值（🔴 **取「教学序 max」= `TEACHING_ORDER.indexOf` 最大者，不是编号数字 max，也不是平均**，见 §2.13 的 v1.3 重大更正），并同步落库 `complexityRank`（0~5）供排序直接使用，写入词典元信息
> - **推荐引擎（`02` §7）**：出题顺序**必须先按 `complexityRank`（或 `TEACHING_ORDER` index）排序，`level` 只用于 UI 分组展示**；🔴 **不得用 `codeComplexity` 字符串直接比较大小**（`'C4' > 'C2'` 为真，但教学上 C4 早于 C2）
> - **CI 断言**：不得存在「`level` 序号更小但 `complexityRank` 更高」被排在前的推荐序列（纳入 `02` 的推荐逻辑单测）；并断言 `complexityRank === TEACHING_ORDER.indexOf(codeComplexity)`（Q-16）
>
> **这正是裁定 B-3 拆分 `codeType`（编码类型）与 `codeComplexity`（教学难度 C1~C6）的价值所在**：只有把「教学难度」独立成一个**可排序**字段（并配 `complexityRank` 数值序），才能支撑「level 定分组、complexity 定顺序」这个解耦。
>
> ⚠️ **`TEACHING_ORDER` 的唯一真源是 `05` §6.2/§6.6**（`['C1','C4','C2','C3','C5','C6']`）。本文档与 `02` **只引用、不另行定义**，以免出现第三处编号/常量碰撞（见 `00` §10.8 的全局 ID 注册表议题）。

### 2.8 L6 · 文章 / 散文（🆕 裁定 G-3：**拆为 L6-a 文言短篇 + L6-b 标准**）

> **为什么要拆（竞析 X-A2-1，主理人已裁定）**：`A2` 给出的 L6 候选里有 **12 篇百字级文言短篇**（《陋室铭》81 字 ~《黄生借书说》200 字），**低于本节原定的「300-1500 字」下限**，也不符合 L4（10-30 字短句）或 L5（诗词）的定位 → **落在体系空档**。裁定拆为两档：
>
> | 档位 | 机器值 | 字数区间 | 内容 | V1 目标量 |
> |---|---|---|---|---|
> | **L6-a** | **`L6a`** | **80-300 字** | 公版**文言短篇**（《陋室铭》《爱莲说》《黄生借书说》等，A2 已给 12 篇候选） | **≥12 篇** |
> | **L6-b** | **`L6b`** | **300-1500 字** | 公版**散文/小说节选**（原 L6 定义） | **≥30 篇** |
>
> 🔴 **关键口径（比拆分本身更重要）：`level` 只定「文体类型/展示分组」，实际出题顺序由 `codeComplexity`（C1~C6）主导**——《陋室铭》81 字含大量文言虚词与生僻码元，其 `codeComplexity` 很可能**高于**部分 L6-b 白话散文，**绝不能假设「L6-a 比 L6-b 简单」而排在其前**。详见 §2.0 末尾的「`level` ≠ 难度」口径块与裁定 B-3。

| 项 | 内容 |
|---|---|
| **语料范围** | **L6-a ≥12 篇（80-300 字文言）+ L6-b ≥30 篇（300-1500 字）**，**全部公版**（须核对作者卒年 + 50 年） |
| **训练目标** | **长文耐力**（U2 文字工作者的核心诉求）+ 速度衰减率的测量载体（CN-E5 需 ≥10 分钟连续练习）。L6-a 兼作**文言文语感**训练（对 U3 考试人群的文言文科目有迁移价值） |
| **章节归属** | 1 篇 = 1 个 `chapterId`；**需支持「无章节」限时模式**（CN-J3 / F9） |
| **🔴 分段续打（CN-G1）** | 打到第 400 字关闭页面，下次提示「上次练到第 400 字，是否继续」，**已完成部分成绩保留**，支持 `Ctrl+S`。**⚠️ L6-a 短篇（80-300 字）通常一次打完，此机制主要服务 L6-b** |
| **🔴 性能达标（CN-G2，阻塞）** | **1500 字长文渲染判定不卡顿：中端笔记本 Chrome 输入延迟 <50ms 无掉帧**（竞品明确翻车点）；1500 字 + 10 分钟累计 5000+ 按键记录下**内存涨幅 <50MB**；**必须固化为 CI 性能门禁** |
| **分段渲染** | 每屏只渲染当前段 ± 1 段（虚拟滚动或分段折叠），避免全量 DOM（`02` §5.2） |
| **双重用途** | ① 耐力训练（CN-G3）② **考试模考语料来源**（CN-F1，NCRE 一级「10 分钟 150 字」需从 **L6a/L6b** 抽取）③ **固定文本每日复测**（CN-C5，建议从 **L6b** 中选一篇 300-500 字固定使用） |

### 2.13 🆕 四维难度模型：语料层级 × 字频档 × 编码类型 × 教学难度（v1.2，回应 `05` §12② + 裁定 B-1/B-2/B-3）

> `05` 指出：本文档的 **`level` 是「语料类型维度」**，而 `05` 的归因需要**「难度维度」**。二者**正交而非冲突**——同一个 L1 层的字，可能是高频 S 档的纯定长字（简单），也可能是低频 C 档的零声母字（困难）。若不显式建模这个正交关系，`05` 无法回答「**到底哪一类难度的用户在流失**」。
>
> 🔴 **裁定 B-3 的关键修正：析客 v1.1 的 `codeComplexity` 与数析的 `codeComplexity` 语义完全不同，且不是一回事，两者都有价值 → 拆成两个字段，都保留。**

| 维度 | 字段 | 取值 | 语义 | 谁定义 / 怎么生成 |
|---|---|---|---|---|
| **① 语料类型** | `level` | `L0 / L0p / L1 / L2 / L3 / L4 / L4C / L5 / L6a / L6b / L6EX / L7`（**12 档**） | **学什么内容**（文体类型 / UI 展示分组）。🔴 **不等于难度**（裁定 G-3） | 本文档 §2.0（构建期由目录结构推导） |
| **② 字频档** | `freqTier` | `S`(前500) / `A`(前1500) / `B`(前3500) / `C`(其余) | **字有多常用**（决定学习价值与复现率） | 本文档 §3.2（构建期**在我方公版语料上自行统计**，见下方 B-2 红线） |
| **③ 编码类型** 🆕 | **`codeType`** | `fixed`(纯定长2键) / `zero-initial`(含零声母，需 `;` 前缀) / `viu-disambig`(含 V/I/U 按位置消歧) | **编码属于哪种规则类型**（决定卡点类型，是新手主要错误源） | 本文档 §3.2（构建期由 `pinyin` 判定；**与 `A1` §2.1 的规则分类一致**） |
| **④ 教学难度** 🆕 | **`codeComplexity`** | `C1`(单韵母) → `C2`(高频复韵母) → `C3`(鼻韵母) → `C4`(特殊声母 zh/ch/sh) → `C5`(零声母) → `C6`(易混对) | **教学难度等级 / 教学顺序** —— 🔴 **这才是 `05` 诊断能力的来源，也是驱动出题顺序与学习路径的字段** | 数析 `05` §6.6 定义分级；本文档定义**取值规则**（见下） |

> 🔴 **`codeComplexity` 的取值规则（裁定 B-3 的核心）：词条级取所含最难码元的 `max`，不是平均。**
>
> **理由**：多字词按平均算会被**系统性低估**。举例：「双拼」两字若一个是 C1、一个是 C4，平均 = **C2.5** → 会让它进入**过早的出题池**，用户在**还没学 zh/ch/sh 特殊声母时就撞上它**，直接产生挫败与流失。
> **取 `max` 才能保证不变式：「词条难度 ≥ 其所有构成码元的已学状态」**——即用户只要遇到某词条，其全部构成码元都必然已学过。🔴 **注意：此处的 `max` 是「教学序 max」，不是「编号数字 max」——见下方 v1.3 重大更正块。**
>
> | 词条 | 各字 C 档 | ❌ 平均（错误） | ✅ `max`（采纳） |
> |---|---|---|---|
> | 「双拼」 | C1 + C4 | C2.5 → 进入过早出题池 | **C4** → 等用户学完 zh/ch/sh 才出现 |
> | 「银行」 | C5 + C1 | C3 | **C5** → 零声母是后期项 |
> | 《陋室铭》(L6a, 81 字) | 含大量文言虚词与生僻码元 | — | **可能 = C6，高于部分 L6b 白话散文** → 故 `level` 不能当难度用（裁定 G-3） |

> ### 🔴🔴 v1.3 重大更正（数析 `05` v3 发现的实现级陷阱，析客原稿确有此缺陷）：`max` **必须按「教学序」取，绝不能按「编号数字」取**
>
> **析客原稿写的是 `max(该词条所有字的 C 档)`，并给出 CI 断言 `codeComplexity === max(...)`——这句话在实现上会被读成「比较 `C1`<`C2`<…<`C6` 的字符串/数字大小」，是错的。**
>
> **根因**：`C1~C6` 的**编号顺序 ≠ 教学顺序**。`05` §6.6 依据 A1 键位表与多信源教学经验给出的真实教学顺序是：
>
> ```ts
> export const TEACHING_ORDER = ['C1', 'C4', 'C2', 'C3', 'C5', 'C6'] as const
> //   C1 单韵母 → C4 特殊声母 zh/ch/sh → C2 高频复韵母 → C3 鼻韵母 → C5 零声母 → C6 易混对
> ```
> **为什么 C4 排第 2**：zh/ch/sh 只有 3 个键，却是**双拼与全拼的首要差异点**——小鹤官方「一小时记键位」的主体就是它。**它编号是 C4，但教学上是第 2 个要学的。**
>
> **数字 `max` 的实测错误率（数析抽验 5 种码元组合，2 种判错 = 40%）**：
>
> | 词条含码元 | ❌ 数字 `max` | ✅ 教学序 `max` | 后果 |
> |---|---|---|---|
> | C1 + C4 | C4 | C4 | ✅ 一致 —— 🔴 **裁定原文与析客原稿举的正是此例，恰好掩盖了问题** |
> | C5 + C1 | C5 | C5 | ✅ 一致 —— **析客的第二个例子也恰好一致，双重掩盖** |
> | **C3 + C4** | **C4** ❌ | **C3** ✅ | 数字 max 判 C4，但用户**早学过 C4、还没学 C3** → 该词被误判「可出题」，用户撞上真正的卡点 C3 |
> | **C2 + C4** | **C4** ❌ | **C2** ✅ | 同上反向：用户学过 C4 未学 C2，却被放进含 C2 的词 |
>
> 🔴 **后果性质与裁定 B-3 想避免的完全相同**——「词条过早进入出题池」。也就是说，**析客原稿的 `max` 规则只解决了「平均会低估」，却没解决「编号序 ≠ 教学序」，仍会以 40% 的概率犯同一个错**。
>
> **✅ 更正后的实现要求（构建期与运行期都必须遵守）**：
> 1. 🔴 **构建期禁止用编号比较**。必须用 `TEACHING_ORDER.indexOf(...)` 取 index 最大者：
>    ```ts
>    const rank = (c: CodeComplexity) => TEACHING_ORDER.indexOf(c)
>    unit.codeComplexity = chars.map(c => c.codeComplexity)
>                               .reduce((a, b) => rank(a) >= rank(b) ? a : b)
>    ```
> 2. 🆕 **落库数值字段 `complexityRank: number`**（= `TEACHING_ORDER.indexOf(codeComplexity)`，取值 0~5），**供排序直接使用**，避免 `02` 推荐引擎与 `05` 指标聚合各自重复实现 index 映射（数析已在其 `IUnitRecord` 加此可选字段，析客采纳为**构建期必填**）。
> 3. 🔴 **`02` §7.2 的出题池准入判定必须用 `complexityRank`（或 `TEACHING_ORDER` index），不得用 `codeComplexity` 字符串比较**。`02` 已同步更正。
> 4. `TEACHING_ORDER` 的**唯一真源是 `05` §6.2/§6.6**；本文档与 `02` 只引用、不另行定义（避免第三处编号碰撞，见 `00` §10.8）。
>
> **CI 断言（Q-16 已按此更正）**：对随机抽样的多字词条，断言 `codeComplexity === 所含码元在 TEACHING_ORDER 中 index 最大者`，**且断言 `complexityRank === TEACHING_ORDER.indexOf(codeComplexity)`**。

**四个维度的实际用途（分工边界）**：

| 消费方 | 用法 | 边界 |

| 🆕 **`codeType`** | `string`（枚举） | 🟡 建议填 | 🔴 **构建期生成** | **编码类型**（裁定 B-3：原 `codeComplexity` **改名**为 `codeType`）：`'fixed'`（纯定长 2 键，无声韵特殊规则）\| `'zero-initial'`（含零声母，需 `;` 或约定前缀）\| `'viu-disambig'`（含 V/I/U 按位置消歧）。**用途：① CI 断言 ② `A1` 键位规则验证 ③ V/I/U 位置消歧标记 ④ `02` 三级提示系统的触发加权**（`zero-initial` 与 `viu-disambig` 是新手主要卡点）。**聚合规则：取全词条的最高优先级类型**（`viu-disambig` > `zero-initial` > `fixed`） | 🆕 新增字段（裁定 B-3）；**与 `A1` §2.1 的规则分类一致** |
| 🆕 **`codeComplexity`** | `string`（枚举） | 🟡 建议填 | 🔴 **构建期生成** | **教学难度等级**（裁定 B-3：采用数析 `05` §6.6 的 C1~C6 值）：`C1`(单韵母) → `C2`(高频复韵母) → `C3`(鼻韵母) → `C4`(特殊声母 zh/ch/sh) → `C5`(零声母) → `C6`(易混对)。**用途：🔴 驱动出题顺序与学习路径——这才是 `05` 诊断能力的来源**（与 `codeType` 用途完全不同，两者都保留、都落库）。<br>🔴 **取值规则（裁定 B-3 核心 + v1.3 更正）：词条级取所含最难码元的「教学序 `max`」，不是平均、也不是编号数字 max。** 理由：① 平均会被系统性低估（「双拼」C1+C4 平均 C2.5 会进过早出题池）② 🔴 **编号序 ≠ 教学序**——真实教学顺序是 `TEACHING_ORDER = ['C1','C4','C2','C3','C5','C6']`（C4 特殊声母排第 2），故必须用 `TEACHING_ORDER.indexOf` 取 index 最大者（数字 max 对 C3+C4/C2+C4 等组合会判错，实测错误率 40%，详见 §2.13 的 v1.3 更正）。长文（L4+）取**全篇教学序 max**，这正是「`level` ≠ 难度」（裁定 G-3）的技术根源 | 🆕 新增字段（裁定 B-3）；C1~C6 分级与 `TEACHING_ORDER` 由 `05` §6.2/§6.6 定义（唯一真源），**本文档只定义取值规则（教学序 max）与 CI 断言** |
| 🆕 **`complexityRank`** | `number`（0~5） | ✅ **必填** | 🔴 **构建期生成** | **= `TEACHING_ORDER.indexOf(codeComplexity)`**（`TEACHING_ORDER` 唯一真源在 `05` §6.2）。例：C1→0、C4→1、C2→2、C3→3、C5→4、C6→5。<br>🔴 **为什么必须落库这个数值序（v1.3 更正）**：`codeComplexity` 是字符串（`'C4' > 'C2'` 字典序为真），但**教学上 C4 早于 C2**。若各处（`02` 推荐引擎、`05` 指标聚合、构建脚本）都自行做 `TEACHING_ORDER.indexOf` 映射，会**重复实现且易写错**。落一个预计算的 `complexityRank` 数值字段，让排序「比大小」这件事有一个**天然有序、无歧义**的字段可用，杜绝「用字符串直接比较 C 档」的 bug。数析已在其 `IUnitRecord` 加此字段（可选），**析客采纳为构建期必填** | 🆕 新增字段（v1.3，数析 §6.6 陷阱处置）；CI 断言见 **Q-16** |
| 🆕 **`acceptedCodes`** | `string[]` | ⚪ **可选**（缺省即 `[name]`） | 🔴 **构建期生成** | **该词条可接受的全部编码口径**（裁定 G-2，A3·S9 已定稿）。**缺省即 `[name]` → 保证现有 380 个词典零改动**。语义：🔴 **`acceptedCodes[0]` 恒为主口径**（零声母场景 **α 口径在前**）；**主口径正确率只用 `[0]` 计算**；**兼容口径命中记 `correct` 但不进主口径分子，单独落 `altCodeHit`**。<br>**为什么需要它**：构建期存在三种不确定性 —— ① `pinyinOverride` 多音字（一词多读音 → 多套编码）② `zeroMap` 零声母 **α/β 双口径**（A1 C-4 的重大信源冲突）③ 方案歧义。**三者在管线末端统一收敛为 `acceptedCodes`，运行期只暴露这一个接口**（运行期不需要知道「为什么有多个口径」）。<br>⚠️ **构建期三套逻辑保留不合并**（各自有独立的校验与断言，见 §8.1 第 ④ 层零声母双口径测试），**只在末端收敛输出** | 🆕 新增字段（裁定 G-2）；运行期判定逻辑改造需 `03` 确认贯穿点 |
| 🆕 **`unitCharCount`** | `number` | ✅ **必填** | 🔴 **构建期生成** | **该词条的汉字字符数**（不含标点、不含注音、不含 `trans`）。例：「快」=1、「银行」=2、「一心一意」=4、L5 诗句「床前明月光，疑是地上霜。」=10（**标点不计**）。<br>🔴 **为什么必须落库（数析 `05` v2 提出的关键副作用）**：`codeType` / `codeComplexity` **取 `max` 聚合会让 `viu-disambig`（及高 C 档）组系统性富集长词组**——因为「只要含一个消歧字，整条就标该值」，而字越多命中的概率越高。**若不同时落 `unitCharCount`，`05` 按此分组统计 LN5 混淆矩阵 / LN1 掌握度时，会把「词更长」误判为「码更难」**，得出错误的归因结论与错误的处方（去强化一个其实不难的码元）。<br>**用途**：`05` 的**字均归一**（per-char normalization）分母。**本文档只保证字段正确，归一化公式由 `05` 定义** | 🆕 新增字段（`05` v2 要求）；CI 断言见 **Q-22** |

```json
  "unitCharCount": 1, "acceptedCodes": ["kk"] }
```

> 🆕 **末 8 个字段由构建期自动生成**（见 §3.3，v1.2 按裁定 A/B/G-2 修订、v1.3 按 X-20 更正）：
> - `unitId` = 全局唯一主键（解决同码不同字反查，X-14）
> - `idealCodeLen` = **纯编码击键数**（双拼恒为 `2 × 字数`；**不含上屏键**，指标层的 `+1` 由 `05` 加，裁定 A）
> - `freqTier` = 字频档（「快」属前 500 高频 → `S`；**由我方公版语料自行统计，禁用第三方词频表**，裁定 B-1/B-2）
> - **`codeType`** = **编码类型**（原 `codeComplexity` **改名**；`k`+`uai` 为纯定长 → `fixed`；若是「安」零声母 `anj` → `zero-initial`，裁定 B-3）
> - **`codeComplexity`** = **教学难度 C1~C6**（数析口径，驱动出题顺序；「快」的 `uai` 属高频复韵母 → `C2`，裁定 B-3）
> - **`complexityRank`** = `TEACHING_ORDER.indexOf(codeComplexity)`；**「快」是 C2，而 `TEACHING_ORDER = ['C1','C4','C2','C3','C5','C6']` 中 C2 的 index = 2**（🔴 v1.3：注意 C2 的 rank 是 2 纯属巧合——**C4 的 rank 是 1**，因为教学上 C4 早于 C2）
> - **`unitCharCount`** = 汉字字符数（「快」= 1；**不含标点/注音/`trans`**）。🔴 **数析 v1.3 发现：`max` 聚合会让高 C 档组富集长词组，缺此字段则「词更长」会被误判为「码更难」**（X-18 / Q-22）
> - **`acceptedCodes`** = 可接受编码口径数组（此字单一口径 → `["kk"]`；缺省即 `[name]`，裁定 G-2）
>
> **这 8 个字段是 `05` 归因分析与 `02` 出题排序的数据基础，贡献者不需关心。**
>
> **对比：零声母字的 `acceptedCodes`（裁定 G-2 + A1 C-4 双口径）**：
> ```json
> { "name": ";ai", "notation": "爱(ài)", "pinyin": "ài", "level": "L1",
>   "codeType": "zero-initial", "codeComplexity": "C5", "complexityRank": 4,
>   "acceptedCodes": [";ai", "ad"] }   // ← [0]=";ai" 为 α 主口径（正确率只用它算）；"ad" 为 β 兼容口径（命中记 correct 但落 altCodeHit）
> ```
> 🔴 **`acceptedCodes[0]` 恒为主口径**（零声母场景 α 在前）；**主口径正确率只用 `[0]` 计算**；兼容口径命中记 `correct` 但不进主口径分子、**单独落 `altCodeHit`**。键位事实以 `A1` §2.1 为准（C-4 双口径为 A1 的重大信源冲突项，待官方核对）。

## 5. 注音格式规范

### 5.1 `notation` 格式（**硬约束，必须与现有正则兼容**）

**格式**：`汉字(pīn yīn)`

**依据**：`Notation.tsx` 已实现 `<ruby>` 注音渲染，正则为 **`/(.+?)\((.+?)\)/g`** + `isKanji()` 判定（F6）。

| 规则 | 说明 | 正例 | 反例 |
|---|---|---|---|
| **R1** | 括号必须是**半角** `(` `)` | `银行(yín háng)` | ❌ `银行（yín háng）`（全角括号不匹配正则） |
| **R2** | 括号内音节之间用**半角空格**分隔 | `中(zhōng)` / `银行(yín háng)` | ❌ `银行(yínháng)` |
| **R3** | **必须带声调符号**（`ā á ǎ à` 等 Unicode 组合字符或预组合字符） | `银行(yín háng)` | ❌ `银行(yin hang)`（无声调 → 失去多音字消歧的价值） |
| **R4** | **多音字必须按词组读音标注**（词组级消歧，CN-B5） | `银行(yín háng)` / `行走(xíng zǒu)` | ❌ `银行(yín xíng)`（**这是竞品的翻车点**） |
| **R5** | 括号前是**纯汉字**（`isKanji()` 需能识别） | `中(zhōng)` | ❌ `zhōng(中)`（顺序反了） |
| **R6** | **上屏轨（L4+）长文本的注音**：整句注音会导致 ruby 渲染过长、视觉噪声大 | 建议 **L4+ 默认不渲染注音**（`02` §5 已定：L4/L5 可选默认关，L6a/L6b/L6EX/L7 关闭） | — |
| **R7** | 中英混输语料的注音：只为 CJK 字符注音，拉丁部分原样保留 | `Tom(tom) 来了` — ⚠️ **实际不建议为混输语料加注音**（视觉混乱），L7 建议 `notation` 与 `name` 相同（不加注音） | — |

### 5.2 `pronunciation` 字段规范（⭐ TTS 巧思，规避多音字/生僻字）

**问题**：把生僻字或多音字直接喂给有道 TTS（`https://dict.youdao.com/dictvoice?audio=X&le=zh`）会**读错**。

**解法（山人码 fork 的巧思，直接采纳）**：`pronunciation` 字段填一个**同音常用字**，喂这个字给 TTS。

| 例 | `notation` 的汉字 | `pronunciation` | 理由 |
|---|---|---|---|
| 山人码示例 | `乙` | **`以`** | 「乙」是多音字/生僻读法风险，「以」是同音常用字，TTS 必读对 |
| 多音字词组 | `银行` | **`银`** 或 `银行`（若 TTS 对词组处理正确） | 词组喂 TTS 时，`yín háng` 的 `行` 有被读成 `xíng` 的风险 → **建议单字逐个喂或选同音常用词** |
| 生僻字 | `蔈` | **`标`** | 生僻字 TTS 可能无发音 |

**取值优先级（`WordPronunciationIcon/index.tsx:11-23` 需增分支，`03` #24）**：
```
pronunciation（若存在）→ notation 的汉字部分 → name
```
**并按默写态择优**（山人码 fork 的做法：在 `pronunciation` / `notation` / `name` 间按默写态选择）。

**⚠️ 降级要求（CN-J7）**：Issue #1036 显示有道 API **对含特殊字符短语返回 500** → 必须**静默降级**（不 alert、不阻塞练习），降级到 `useSpeech.ts` 的 SpeechSynthesis，仍失败则静默无音。

### 5.3 `split` 字段规范

| 层级 | `split` 内容 | 示例 |
|---|---|---|
| L0 / L0' / L1 | **声母 + 韵母** | `zh + ong`（中）/ `k + uai`（快） |
| L2 / L3 | **逐字声韵拆分**，用空格分隔 | `yín + háng`（银行）/ `yī + xīn + yī + yì`（一心一意） |
| L4+ | **留空**（上屏轨不需要拆分提示） | `""` |

⚠️ **只填声韵拆分，不填字根拆分**（「只做音码」边界，CP-1.3 / NG-6）。

### 5.4 多音字的「多读音全接受」判定规则（CN-B5）

> **硬约束：一个字的多个合法读音在判定时均视为正确。**

| 场景 | 处置 |
|---|---|
| `notation` 标注的是词组级消歧后的**主读音** | 用于展示与 TTS |
| **判定时** | **该字的全部合法读音对应的编码均判正确**（如「行」在「银行」中读 `háng`，但用户打 `xíng` 的编码……⚠️ **此处需谨慎**：对码轨下判定的对象是**编码**，若允许 `xíng` 的编码也判对，会削弱词组级消歧的训练价值） |
| **析客建议的处置** | ① **对码轨（L0'~L3）**：只接受**词组级消歧后的主读音编码**（因为这是训练目标——用户必须知道「银行」的「行」读 `háng`）② **上屏轨（L4+）**：只要**上屏的汉字正确**即判对，**不追究用户用的是哪个读音的编码**（因为 IME 内部行为不可见）③ **单字层级（L1）**：接受**全部合法读音的编码**（因为孤立单字无上下文，无法消歧） |
| **一键反馈入口** | 提供「**这个读音不对**」按钮（CN-B5），用户可举报消歧错误 → 记录到本地 + 提供导出为 Issue 的模板 |

> ⚠️ **这是跨文档待确认项**：「多读音全接受」与「词组级消歧的训练价值」存在张力。本文档建议按层级差异化处置（上表），**需产品负责人确认**。见 §14 X-2。

### 5.5 出题池排除规则（数据质量兜底）

| 排除类别 | 理由 | 依据 |
|---|---|---|
| **多口径字**（如「嗯」，不同词典/输入法按 `en`/`eng`/`n` 处理） | 「**不适合作为唯一校准样本**」 | A1 §3.5（S2 原文提醒） |
| **A1 C-1/C-2 待核对项涉及的字**（「儿、二、耳」「军、群、云」） | **键位映射未三信源确认，禁止猜测填充**（CR-5） | A1 §2.3：「**在确认前，该组字暂不进入出题池**」 |
| **生僻字**（超出《通用规范汉字表》一级字表 3500 字且非 L6EX 专用） | ① TTS 可能无发音 ② 用户不认识 → 无法形成有效练习 ③ 官方码表交叉验证的 27 处差异**全部是生僻多音字的读音取舍差异** | `Shuang` 的「无拼音模式移除多音字 & 生僻字」策略；A1 §5.3；**裁定 G-1：生僻字检测基准与 A2:611 的 A-10 同源（均为一级字表）** |
| **同一字符重复 ≥3 次的串** | CP-2「语料必须真实」 | CI 断言 |

## 7. 多音字处理策略（CN-B5，**数据质量生死线**）

### 7.1 为什么这是生死线

> **竞品明确翻车**（`06`/`07` I8）：「**有些多音字的拼音处理的不好，标出来的不是正确的读音。**」
>
> 后果链：注音标错 → 用户看到「银行(yín xíng)」→ 用户困惑（「这不是错了吗？」）→ **对整个产品的数据质量失去信任** → 而数据质量是打字练习产品的**唯一护城河**（用户不会因为 UI 丑离开，但会因为「练错了」离开）。

### 7.2 策略：**离线预处理，而非运行时字级 lazy 转换**

| 维度 | 离线预处理（**采用**） | 运行时字级 lazy 转换（**不采用**） |
|---|---|---|
| 消歧质量 | ✅ **词组级消歧**（有完整上下文） | ❌ 字级转换无上下文 → 「银行」的「行」必然读错 |
| 运行时性能 | ✅ **零开销**（查表） | ❌ 每次渲染都要跑拼音库 |
| Bundle 体积 | ✅ **运行时零拼音库依赖**（TC-3） | ❌ +~100KB |
| 可 review 性 | ✅ **产物是静态 JSON，可 diff、可人工校对** | ❌ 运行时行为不可 review |
| 可测试性 | ✅ CI 可全量检测 | ❌ 难以覆盖 |

### 7.3 词组级消歧示例（**可直接作为 CI 黄金用例集**）

| 词组 | ✅ 正确消歧 | ❌ 字级转换的错误结果 | 消歧依据 |
|---|---|---|---|
| **银行** | `yín háng` | `yín xíng` | 「行」在金融机构义项读 `háng` |
| **行走** | `xíng zǒu` | `háng zǒu` | 「行」在走动义项读 `xíng` |
| **音乐** | `yīn yuè` | `yīn lè` | 「乐」在音乐义项读 `yuè` |
| **乐趣** | `lè qù` | `yuè qù` | 「乐」在快乐义项读 `lè` |
| **重庆** | `chóng qìng` | `zhòng qìng` | 地名，「重」读 `chóng` |
| **重量** | `zhòng liàng` | `chóng liàng` | 「重」在分量义项读 `zhòng` |
| **长大** | `zhǎng dà` | `cháng dà` | 「长」在生长义项读 `zhǎng` |
| **长度** | `cháng dù` | `zhǎng dù` | 「长」在距离义项读 `cháng` |
| **地道**（副词，「相当地道」） | `dì dao`（轻声） | `dì dào` | ⚠️ **轻声是消歧的难点**，需专门处理 |
| **差点儿** | `chà diǎnr` | `chā diǎnr` | 「差」有 4 个读音（chā/chà/chāi/cī） |

> **⚠️ 轻声与儿化音**：这是多音字之外**第二个数据质量风险点**，`pinyin-pro` 对轻声的处理需实测验证。**建议 V1 语料尽量避免轻声词密集的内容**（如口语化对话），L4-C 聊天短句层需特别检查。

### 7.4 准确率验收（**≥99.5%**）

| 验收方式 | 规格 |
|---|---|
| **① 全量自动检测** | 构建脚本 Step 4 输出《多音字检测报告》：列出**全部多音字出现位置、选定读音、置信度**。低置信度项**必须人工复核** |
| **② 人工抽检 200 条** | 从全部含多音字的词条中随机抽 200 条人工核对。**准确率 ≥99.5%**（即最多 1 条错误） |
| **③ 分层阈值（析客建议，待确认）** | **高频词（前 1000）≥99.9%** / **长尾词 ≥99%**。理由：高频词的错误影响面大 10 倍以上 |
| **④ CI 断言** | §7.3 的黄金用例集**必须 100% 通过**（这不是抽样，是全量断言） |
| **⑤ 一键反馈入口** | 「**这个读音不对**」按钮（CN-B5）→ 本地记录 + 提供导出为 GitHub Issue 的模板 |

### 7.5 判定时「多读音全接受」的处置

见 §5.4（**建议按层级差异化处置：对码轨只接受主读音编码；上屏轨只要汉字正确即判对；L1 单字接受全部合法读音**）。⚠️ **跨文档待确认项，见 §14 X-2。**

### 7.6 出题池排除（数据质量兜底）

**参考 `Shuang` 的做法：「无拼音模式移除多音字 & 生僻字」**（`02` §7.4 的四种出题模式之一）。

**我方采用**：
- **默认出题池**：包含多音字（因为多音字消歧是我们的强项，且真实语料无法回避）
- **「无拼音」出题模式**：**移除多音字与生僻字**（供用户在数据质量存疑时选择，也作为 A1 待核对项的兜底）
- **强制排除**：多口径字（「嗯」）、A1 C-1/C-2 涉及字（「儿/二/耳」「军/群/云」）**在核对完成前不入池**（§5.5）

### 9.2 各层级每章容量建议（**含理由**）

| 层级 | 每章容量 | 理由 |
|---|---|---|
| **L0**（全拼声韵母） | 10-15 | 认知性内容，容量可略大 |

| **L6b**（文章/散文） | **1 篇 = 1 章**（300-1500 字） | 需配合分段续打（CN-G1）与「无章节」支持 |

| **L7**（标点专项） | **5-10** | 每条含密集标点，认知负荷高 |

### 9.3 「无章节」模式的处理（考试限时 + 长文）

### 10.2 导入流程（**全本地，🔴 隐私红线**）

```
[用户选择 TXT/JSON 文件]
        │
        ▼
[本地解析]  ← 🔴 全过程本地完成，不上传用户文本到任何服务器（CR-6）
        │
        ▼
[本地分词]  ← 复用构建期管线的 Step 3（打包为 Web Worker 或 wasm 以不阻塞主线程）
        │
        ▼
[按当前方案生成编码与注音]  ← Step 4~8
        │   ⚠️ 这里需要拼音能力 → 两个选项：
        │   (a) 把 pinyin-pro 打进一个「导入专用」的懒加载 chunk（不进主 bundle）
        │   (b) 走在线 API
        │   🔴 若走 (b)，必须获得用户明确同意（弹窗 + 勾选，不得默认勾选）= 隐私红线
        │   ⭐ 析客建议：采用 (a)，懒加载 chunk 只在用户主动导入时才下载
        ▼
[多音字检测 + 报告]  ← 显示「发现 N 个多音字，已按词组消歧，请核对：…」
        │
        ▼
[预览 + 编辑]  ← 用户可修正注音、调整分章
        │
        ▼
[保存到 IndexedDB]  ← 新增「自定义词典表」（Dexie v4，CN-J6）
        │
        ▼
[在词典选择页与内置词典并列展示，带「自定义」标记]
```

### 10.3 自定义方案 JSON 导入（CN-H1）

| 规格 | 说明 |
|---|---|
| **格式** | 借鉴 `{keyMap, zeroMap}` **思路**（A1 §6.2），但**结构化表达**（不用斜杠分隔字符串，以获得类型安全与构建期校验） |
| **校验失败** | **给出具体错误定位**（字段名 + 期望类型 + 实际值），不能只说「格式错误」 |
| **🔴 拒绝「一对多」映射并告知原因** | 「单个双拼输入对应多个可能拼音会导致重码率上升」（纸砚亦未兼容，A1 C-11）。⚠️ 但**「同键承载声母 + 韵母」（V/I/U 三键）属于按位置消歧，不属于一对多重码**，**必须允许** |
| **`zeroMap` 值必须是数组** | 支持多口径（α/β），这是我方相对全部竞品的原创增量（A1 §6.2） |
| **展示** | 方案选择器中带「自定义」标记；可导出分享 |

### 10.4 导出

| 规格 | 说明 |
|---|---|
| **格式** | JSON（与产物 schema 一致），便于分享与备份 |
| **内容** | 词条 + 词典元信息 + `chapterName[]`/`chapterNum[]` |
| **隐私** | **全本地生成文件，无任何网络请求**（CN-E7） |
| **不含** | ❌ 用户的练习记录（那属于 `data-export.ts` 的 DB 导出，是另一条链路） |

### 10.5 数据导入导出的去重与确认（**竞品必采设计**）

> **来源（`06`）**：按 id 去重 + **两步确认**（先显示找到几条记录，再选合并或替换），「**同一份文件导入两次不会翻倍**」。

| 步骤 | 行为 |
|---|---|
| **Step 1** | 用户选择文件 → 解析 → 显示「**找到 N 条记录**（其中 M 条与现有数据 id 重复）」 |
| **Step 2** | 用户选择：① **合并**（跳过重复项，只导入新的）② **替换**（覆盖重复项）③ 取消 |
| **Step 3** | 执行 + 显示结果「导入 X 条，跳过 Y 条重复，覆盖 Z 条」 |

> ⚠️ 现有 `importDatabase` 已开 `acceptVersionDiff:true` 与 `clearTablesBeforeImport:true`（`03` §1.5）→ **`clearTablesBeforeImport` 会清空表**，这与「合并」语义冲突。**自定义词典导入不得复用 `importDatabase`，需独立的合并逻辑。**


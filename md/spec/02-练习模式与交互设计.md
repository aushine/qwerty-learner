## 📌 TL;DR

中文练习采用**双轨输入判定**：**对码学习轨 `code-match`**（绕过系统 IME，捕获原始按键，按方案码表校验编码，无候选窗、无选词，打对自动进下一字；适用**字 / 词 / 成语**）与**上屏实战轨 `ime`**（用户用真实输入法在输入框打字，`compositionend` 取 `e.data` 与目标文本 diff；适用**句子 / 诗句 / 文章**）。两轨的**指标口径分开定义、分开标注、分开存储（`track: 'code' | 'ime'`），不得混算，不得出现「综合分」**。

对码轨的按键捕获采用 **`<input type="password">` 强制关闭 IME + `KeyboardEvent.code` 物理键位** 的组合方案（Issue #744 的已验证解法，fork `9376c37` 自 2024-01-21 生产在用 16 个月），**并配套「卡住三档训练轮」+「开始/暂停状态机」防止脏数据**；⭐ **提示过的题不计入「独立正确率」，单独统计为「依赖提示率」**——这本身就是最好的学习进度指标（应从 100% 逐步降到 0%）。

上屏实战轨必须**重写**现有 `TextAreaHandler`（其 `onCompositionStart` 直接 `alert('您正在使用输入法，请关闭输入法。')` 恰是 Issue #744 根源，而实战轨恰恰需要 composition），且必须修复「一次上屏多字只校验末位字符」的 Bug。

交互层最重要的三条不可协商约束：**① 过程指标必须用自我对比框架（▲▼ / 比昨天 +/-），禁止绝对评价；② S1-S3 阶段「字/分」必须视觉降级且必须紧跟社区经验值对照；③ 全站禁止红色/警告色用于速度下降，对比基准永远是昨天的自己。**

## 1. 双轨模式总览

### 1.1 为什么必须双轨（D1 决策依据）

单一判定机制无法同时满足两类完全不同的训练目标：

| 训练目标 | 需要什么 | 单一机制为什么不行 |
|---|---|---|
| **键位记忆**（S1-S3，U1 核心诉求） | 精确到「每一个键」的判定与反应时；**不能有候选窗**（候选窗会引入「选词」这个与键位记忆无关的认知负荷） | 用真 IME：输入法会自动补全/纠错/联想，**成语会被自动补全，反而失去练习意义**；且一次上屏多字 → **字级 timing 不可得**，反应时与韵母掌握度全部失真 |
| **真实打字能力**（S4+，U2/U3 核心诉求） | 必须用**用户自己的真实输入法**（含词组联想、纠错、候选窗），因为「练的不是实验室场景」 | 用对码轨：**没有选词、没有词组联想、没有标点全角/半角**，与真实打字场景脱节，测出的 CPM 无参考价值 |

> **决定性论据（F3）**：现有 `TextAreaHandler/index.tsx:48-50` 的 `onCompositionStart={() => alert('您正在使用输入法，请关闭输入法。')}` **正是 Issue #744 的根源**。而上屏实战轨**恰恰需要 composition**。因此这不是「优化现有逻辑」，而是**必须物理分离两个 handler**。

### 1.2 双轨对照表（**本表的口径必须在全站一致**）

| 维度 | 对码学习轨 `code-match` | 上屏实战轨 `ime` |
|---|---|---|
| **词典字段** | `inputMode: 'code-match'` | `inputMode: 'ime'` |
| **机制** | 绕过系统 IME，捕获**原始按键**（`KeyboardEvent.code` 物理键位），按方案码表逐字符校验编码 | 用户用**真实输入法**在输入框打字，`compositionend` 取 `e.data` 上屏文本与目标文本 diff |
| **输入元素** | `<input type="password" autocomplete="new-password">`（0×0 隐藏，`h-0 w-0 appearance-none`） | 普通 `<textarea>`（**不能是 password**，password 与 IME 互斥） |
| **候选窗 / 选词** | ❌ 无 | ✅ 有（用户系统输入法的真实候选窗） |
| **接受字符集** | **仅 `a-z` 与半角分号 `;`**（分号用于微软双拼 `ing→;`） | 任意（含全角标点、汉字、拉丁、数字） |
| **适用语料层级** | **L0' 韵母分组 / L1 单字 / L2 词组 / L3 成语** | **L4 短句 / L4C 聊天 / L5 诗句 / L6a 文言短篇 / L6b 文章 / L6EX 公文 / L7 标点混输**（🆕 裁定 G-3：原 L6 已拆 a/b） |
| **判定单位** | **码元（键）**。🆕 **裁定 G-2：命中判定改用 `acceptedCodes`**——`acceptedCodes[0]` 为主口径（进正确率分子），其余为兼容口径（记 `correct` 但单独落 `altCodeHit`）；缺省即 `[name]` | **上屏段 → 逐字符**（一次上屏多字时每字都需校验） |
| **前进方式** | **打对自动进下一字，无需按空格** | 上屏即校验；打出最后一个字（句末「。」）自动结算或随时点「完成」 |
| **计时起点** | 第一次合法按键的瞬间 | **按下第一个键的瞬间**（**不是第一个字上屏时**，此前停留多久都不计时）——CPM 权威口径 |
| **指标口径组** | 已掌握韵母数/总数、**击键**（键/秒）、**码长**（键/字）、编码正确率、平均反应时、**独立正确率 / 按键正确率 / 依赖提示率（三分口径）**、回改、连击、键准、键法（左右手均衡） | **CPM**（字/分，上屏字数口径）、字准确率、有效字数、回改次数、退格次数、回改率、**IME 辅助上屏数**（与零辅助上屏数分开）、整句一次上屏率、**速度衰减率** |
| **DB 标记** | `track: 'code'` | `track: 'ime'` |
| **精度边界（必须诚实标注）** | ⚠️ **选重与打词率无法采集**（没有选词动作）；不反映真实打字场景的候选窗行为 | ⚠️ **反应时与韵母掌握度不可信**（一次上屏多字，字级 timing 不可得）；⚠️ **选重与打词率精度受 IME 行为影响 → UI 须标注「尽力统计，仅供参考」，不得承诺精确** |
| **移动端** | ⚠️ 技术上几乎不成立（软键盘拿不到原始 `keydown`）→ 降级为「点 `SchemeKeyboard` 键位图输入」 | 🟡 可用（移动端输入法本身即 IME），但**不是主力练习场景** |
| **技术风险** | 🔴 **Spike S1 阻塞**（`password` 强制关闭 IME 属「事实可用但无规范契约保证」） | 🟠 三浏览器 composition 事件顺序不一致（§3.1） |
| **新增文件** | `PasswordKeyHandler/` | `ImeCompositionHandler/` |
| **`03` 贯穿点** | #13 #14 #16 #19 #23 | #13 #15 #17 #18 #19 #20 #21 #12 |

### 1.3 ⛔ 三条不可违反的口径纪律

1. **两套指标口径必须分开定义、分开标注，不得混算，不得出现「综合分」**（D1）
2. **DB 记录必须带 `track: 'code' | 'ime'` 标记分开存储**（D1 / CN-J6）
3. **不得复用 `ChapterRecord.wpm` getter**（F11：现有口径是「词/分」= `Math.round(wordCount/time*60)`，中文必须另立「字/分」，否则中英数据混算）

### 1.4 分发实现（F1，唯一分发点）

```ts
// src/pages/Typing/components/WordPanel/components/InputHandler/index.tsx:11-24
// 现状（F1）：switch (dictInfo.language) { en/de/romaji → KeyEventHandler; code/default → TextAreaHandler }
// 改造后（03 #13）：language + resolveInputMode(dictInfo) 联合分发
switch (true) {
  case lang === 'zh' && mode === 'code-match': return <PasswordKeyHandler   updateInput={updateInput} />
  case lang === 'zh' && mode === 'ime':        return <ImeCompositionHandler updateInput={updateInput} />
  case ['en','de','romaji'].includes(lang):    return <KeyEventHandler       updateInput={updateInput} />
  default:                                     return <TextAreaHandler       updateInput={updateInput} />
}
```

**向后兼容保证**：`inputMode` 为**可选字段 + 缺省 `code-match`**（`resolveInputMode(dict) = dict.inputMode ?? 'code-match'`），现有 **380 个词典**的路由与行为**完全不变**。

## 2. 对码学习模式详细设计（CN-A1 / A1a / A1b）

### 2.1 按键捕获方案对比与选择（**CN-A1a，Spike S1 门禁**）

| 方案 | 机制 | 优点 | 缺点 | 生产背书 |
|---|---|---|---|---|
| **方案 A：`<input type="password">`** | 浏览器/OS 层对密码输入框**强制关闭 IME**（Windows IME / macOS 输入法 / Linux ibus 行为一致），配合 `keydown` 取原始按键 | ① **无需 JS 干预**即可关闭 IME ② 沿用现有 `TextAreaHandler` 的焦点管理模式（`isTyping` 时 focus，`onBlur` 自动夺回，F3）③ 元素 0×0 隐藏，掩码圆点视觉不可见 | ① 密码管理器弹「是否保存密码」② Edge reveal 图标 ③ autofill 黄底 ④ **屏幕阅读器播报为「密码编辑框」= 真实 a11y 缺陷，无法完全消除** ⑤ **永久无法通过真 IME 输入汉字**（故只能用于对码轨）⑥ 属「事实可用但无规范契约保证」 | ⭐ **fork `9376c37`（2024-01-21 上线，至 2025-05-21 持续在用，服务山人码 LTS 社区，未见兼容性 issue 回报）** |
| **方案 B：`KeyboardEvent.code` 物理键位直捕** | `window.addEventListener('keydown')` 取 `e.code`（如 `KeyA` / `Semicolon`），不依赖任何输入元素 | ① **键盘布局无关**（Dvorak/Colemak 用户也能练 QWERTY 双拼键位）② **`Semicolon` 的 `event.code` 稳定**，规避微软双拼分号键在网页/远程桌面/快捷键软件中被拦截的风险（A1 §4.5）③ 不受系统输入法方案、模糊音、自定义映射影响 ④ 移动端可点键位图产生等价 `code` ⑤ 无 a11y 语义缺陷 | ① 全局监听需处理**快捷键冲突**（浏览器 Ctrl+T/W、扩展快捷键）② 需自行管理「练习中/未练习中」的监听开关（现有 `KeyEventHandler` 已有此模式，F2）③ **IME 组合期 `e.key === 'Process'`，`e.code` 仍为物理键 → 需要判定策略**（见下）④ 若用户处于中文态，**按键仍会被 IME 消费**（`keydown` 能收到但 IME 候选窗也会弹出）→ **需要方案 A 或「要求用户手动切英文态」配合** | `Return7-T/Shuang` 与 `shuangpin-practice` 的共识做法（**要求切英文输入法 + 不用 input 框**） |

#### ⭐ 选择结论：**A + B 组合（推荐）**

| 层 | 采用 | 理由 |
|---|---|---|
| **焦点/IME 抑制层** | **方案 A（`type="password"`）** | 让浏览器/OS 帮我们关闭 IME，**不需要用户手动切换输入法**（这是竞品「要求切英文输入法」做法的用户体验短板），也不依赖用户记住切换 |
| **取值层** | **方案 B（`KeyboardEvent.code`）** | 从 `keydown` 事件取 `e.code` 而非 `e.key`，获得**键盘布局无关性**与**分号键稳定性**；映射 `KeyA→'a'`、`Semicolon→';'`，其余 `code` 一律忽略 |
| **兜底层** | 若非 password 环境（如某些浏览器策略）检测到 IME 介入（`e.key === 'Process'` 或 `compositionstart` 触发），**弹非阻塞提示**「请切换到英文输入法」，**不 alert、不判错** | Web 无 API 可程序化切换输入法态（TC-4） |

**接受的字符集（硬约束）**：**仅 `KeyA`~`KeyZ` 与 `Semicolon`**（对应 `Return7-T/Shuang` 的「输入内容只能为字母或半角分号 `;`」约定）。其余按键**不产生输入但也不报错**（避免用户误触产生困惑）。

#### `type="password"` 的完整代价清单与缓解（**必须在代码注释中留痕**）

| 代价 | 严重度 | 缓解手段 |
|---|---|---|
| 密码管理器弹「是否保存密码」 | 中 | `autocomplete="new-password"`（**比 `off` 更有效**）+ 随机化 `name` 属性 |

### 2.2 逐字符校验与「打对自动前进」

#### 复用现有引擎（**核心洞察：校验层零改动**）

现有 `Word/index.tsx:168-235` 的逐字符校验 useEffect **对码轨可原样复用**，因为它只比较 `inputWord` 最后一个字符与 `displayWord` 同位置字符——而对码轨下 `displayWord` = **拉丁编码**（如小鹤双拼「中」= `vs`），用户敲的也是拉丁字母，**逐字符校验天然适用**。

这正是山人码 fork 的决定性实证：**校验引擎、DB、WPM 公式一行未动，核心引擎改动 <30 行**（D3）。数据结构范式：

```json
{ "name": "vs",           // ← 用户实际敲的键序列（编码，构建期生成）
  "notation": "中(zhōng)", // ← 展示用汉字（ruby 注音渲染）
  "trans": ["…"],
  "split": "zh + ong",     // ← 拆分/提示（Phonetic 位置展示）
  "pronunciation": "中",    // ← 朗读用：喂同音常用字给 TTS，规避多音字/生僻字发音错误
  "chapterId": 0 }          // ← 自定义章节归属
```

这与日语 romaji 词典（`name`=罗马音、`notation`=假名）**完全同构**，是同一条数据抽象的**第三次复用**（F6：`Word/index.tsx:290` 的 `['romaji','hapin']` 白名单加 `'zh'` 即可，**1 行改动**）。

### 2.3 卡住自动提示：三档训练轮（**竞品 P0 必采设计**）

> 来源：`Return7-T/Shuang` 与 `shuangpin-practice` 的共识做法 + ulpb 七天上手路径 Day1-3「开启显示提示当训练轮」（「按错会直接告诉你正确答案，几次之后自然就记住了，不用刻意背」）。

| 档 | 触发条件 | 行为 | 是否计入「依赖提示」 |
|---|---|---|---|
| **第 1 档：键位闪烁** | **干等 3 秒**（无任何按键） | `SchemeKeyboard` 上**闪烁该按的键**（**只闪键位，不给答案文字**）；**用户敲键后重新计时**（3 秒重新起算） | ✅ **计入**（`hintUsed = 'flash'`） |
| **第 2 档：主动看答案** | 用户按 **`Tab`** | 显示完整答案（编码 + 拼音 + 拆分）；该题标记为已看答案 | ✅ **计入**（`hintUsed = 'answer'`） |
| **第 3 档：自动显示答案** | 设置项开启后，**干等 6 秒** | 自动显示答案（等同第 2 档）；**默认关闭** | ✅ **计入**（`hintUsed = 'auto'`） |

#### 🆕 裁定 B-3 落地：提示阈值按 `codeType` 加权（**引用 `04` v1.2 §3.2 的字段，本文档只消费不定义**）

上表的「干等 3 秒 / 6 秒」是**基准阈值**。裁定 B-3 把原先混在一起的两个字段拆开后，**提示系统的加权项应引用 `codeType`（编码类型），不是 `codeComplexity`（教学难度）**：

| `codeType` | 语义 | 提示延迟倍率 | 理由 |
|---|---|---|---|
| **`fixed`** | 纯定长 2 键，无声韵特殊规则 | **×1.0（基准 3 秒）** | 规则最简单，应尽快让用户自己回忆，过多提示会削弱记忆形成 |
| **`zero-initial`** | 含零声母，需 `;` 或约定前缀 | **×0.7（约 2 秒）** | 🔴 **新手主要卡点之一**：零声母的「要不要加前缀」是规则性困惑，不是记忆性困惑 → 早点给提示，避免用户反复试错产生「双拼好难」的错误归因 |
| **`viu-disambig`** | 含 V/I/U 按位置消歧 | **×0.7（约 2 秒）** | 🔴 **同上**：V/I/U 的位置消歧是规则学习，用户此刻还没建立规则模型，干等无益 |

> **为什么用 `codeType` 而不是 `codeComplexity` 做提示加权**（裁定 B-3 的分工）：
> - **`codeType`（3 值）回答「这是哪一类规则」** → 提示系统需要知道的是「用户卡在规则上还是卡在记忆上」，**规则性困惑应更早提示**（提示内容是规则说明），记忆性困惑应更晚提示（提示方式是闪键位，逼用户回忆）
> - **`codeComplexity`（C1~C6）回答「这是第几教学阶段」** → 它驱动的是**出题顺序**（见 §5.1 的裁定 G-3 口径块），不是提示时机
>
> 🔴 **两字段的消费方完全不同，不得混用**（这是裁定 B-3 拆分的核心价值）。
>
> **可选增强（`codeComplexity` 的第二用途）**：在用户**刚进入某 C 档**（如首次遇到 C4 特殊声母 zh/ch/sh）时，**前 N 题临时把提示延迟再 ×0.8**，帮助跨过规则切换的门槛；N 题后恢复。**此为 Should 级增强，V1.0 可不做**（需 `05` 提供「刚进入某档」的判定口径）。

#### ⭐ 核心设计原则（**这是本项目相对全部竞品的指标创新**）

1. **提示过的题不计入「独立正确率」，单独统计为「依赖提示」**
2. **combo（连击）在使用提示时中断**
3. **「依赖提示率」本身就是最好的学习进度指标**——它应从 **~100%（Day 1）逐步降到 0%（Day 14+）**，比正确率更灵敏（因为正确率在提示下会虚高）
4. **只闪键位不给答案**（第 1 档）是刻意的：给答案 = 用户看到答案后照抄，键位记忆未形成；闪键位 = 用户仍需自己回忆「这个键是哪个韵母」

#### 提示总开关（设置页）

| 设置项 | 默认 | 说明 |
|---|---|---|
| `hintEnabled`（独立提示总开关） | **开** | 关闭后三档全部失效 = 等同「无提示毕业模式」（CN-C3a） |
| `hintFlashDelay` | **3 秒**（可调 1-10 秒，可关） | 第 1 档触发延迟 |
| `hintAutoAnswer` | **关** | 第 3 档开关 |
| `hintAutoAnswerDelay` | **6 秒** | 第 3 档延迟（仅在 `hintAutoAnswer` 开启时生效） |

### 2.4 开始 / 暂停状态机（**防脏数据，竞品 P0 必采设计**）

> 来源：`shuangpin-practice` 的状态机设计（其单测覆盖了状态机）。**这是数据可信度的前提**——没有状态机，用户切标签页回来的时间会被计入用时，卡住提示会在暂停期触发，反应时数据全部失真。

#### 状态定义

| 状态 | 名称 | 进入条件 | 题面显示 | 键位图显示 | 接收输入 | 计入用时 | 触发卡住提示 | 误触是否计错 |
|---|---|---|---|---|---|---|---|---|
| **S0** | `idle`（未开始） | 页面加载完成 | ✅ 显示 | ✅ 显示 | ❌ | ❌ | ❌ | **❌ 不计错** |
| **S1** | `running`（进行中） | S0 下按 `空格` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ 计错 |
| **S2** | `paused`（暂停） | S1 下按 `Esc` / **切走标签页（`visibilitychange`）** / **无输入超时（默认 60 秒，可调可关）** / `window blur`（现有行为，`Typing/index.tsx:65-74`） | ✅ | ✅ | ❌ | **❌ 不计入用时** | **❌ 不触发** | ❌ 不计错 |
| **S3** | `finished`（已结算） | 打完最后一个字 / 模考时间到（CN-F1） | 结算页 | — | ❌ | ❌ | ❌ | — |

#### 状态转移图

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
   [页面加载]        ▼                                          │
  ─────────────► S0 idle ──按 空格 ──► S1 running ──打完──► S3 finished
                    ▲                    │    ▲
                    │                    │    │
                    │        按 Esc / 切走标签页 / 无输入超时 / blur
                    │                    ▼    │
                    │                 S2 paused
                    │                    │
                    └──按 重开 ───────────┤
                                         │
                          「离开较久」后恢复：本题重新开始
                          （那段时间闪过的提示不算看过）
```

#### 关键规则（**必须逐条实现并单测**）

| # | 规则 | 理由 |
|---|---|---|
| **R1** | **S0 期间误触不计错** | 页面加载 = 「未开始」态，题面与键位图先显示，**用户可先切输入法、先看键位图**，此时的任何按键都不应产生错误记录 |
| **R2** | **`空格` 开始** | 明确的「我准备好了」信号；`空格` 本身不作为输入字符 |
| **R3** | **`Esc` 暂停** | 与现有行为对齐；暂停期间**不接收输入、不计入用时、不触发卡住提示** |
| **R4** | **切走标签页自动暂停**（`document.visibilitychange`） | 防止用户去查键位表的时间被计入用时（会污染反应时数据） |
| **R5** | **无输入超时自动暂停**（默认 **60 秒**，可调，可关） | 用户去干别的事了，不应继续计时；**与「卡住 3 秒提示」是两个不同机制**（前者是分钟级暂停，后者是秒级提示） |
| **R6** | ⭐ **「离开较久」后恢复则本题重新开始** | **那段时间闪过的提示不算看过**，否则该题会被误记为「依赖提示」→ 污染依赖提示率这个核心指标。「较久」的定义：**暂停时长 > 卡住提示延迟（默认 3 秒）** |
| **R7** | 暂停态下按任意键**不产生输入**，仅 `空格`/`Esc` 可恢复 | 防止恢复瞬间的误触 |
| **R8** | **计时从按下第一个键的瞬间开始**（不是第一个字上屏时，也不是进入页面时） | CPM 权威口径（recatools）；此前停留多久都不计时 |

## 3. 上屏实战模式详细设计（CN-A2 / A2a）

### 3.1 composition 事件处理（**跨浏览器时序差异是本轨最大的坑**）

#### 🔴 硬约束：**必须直接监听 `compositionend` 取 `e.data`，不得依赖 `input` 事件的 `isComposing` 时序**

三浏览器的事件顺序**不一致**：

| 浏览器 | 事件顺序 | 影响 |
|---|---|---|
| **Chrome / Edge** | `compositionstart` → `compositionupdate`* → **`compositionend`** → `input`（**`isComposing: false`，补发**） | 若依赖 `input` 事件，会拿到一次 `isComposing:false` 的补发 input，**可能被误判为「非组合输入」而丢弃或重复处理** |
| **Safari** | `compositionstart` → `compositionupdate`* → `input`（`isComposing: true`）→ **`compositionend`（在最后一个 `input` 之后）** | 若依赖 `input` 事件，**`compositionend` 尚未触发**，此时取 `textarea.value` 会拿到不完整的中间态 |
| **Firefox** | 与上述两者**又不同**（历史上 `compositionend` 与 `input` 的相对顺序有过变更） | 同上 |

> **现有代码的 Bug（F3）**：`TextAreaHandler/index.tsx:23` 的 `if (!nativeEvent.isComposing && nativeEvent.data !== null)` —— 这个判定在 Chrome 下会**接住 compositionend 后补发的那个 input 事件**，在 Safari 下会**丢弃全部组合期输入**。两种行为都不是我们要的。

#### 正确实现（`ImeCompositionHandler`）

```
compositionstart  → 置内部 isComposing = true
                    ★ 不 alert、不 return（与现 TextAreaHandler:48-50 相反）
                    可选：把当前拼音串以浅灰显示在目标文本下方（候选态回显）

compositionupdate → e.data = 'j' → 'ji' → 'jin' → …
                    ★ 仅用于 UI 回显，不参与校验、不写 state

compositionend    → e.data = '今天'（本次上屏的完整文本）
                    ★ 唯一可信数据源
                    清空 textarea.value（沿用 TextAreaHandler:26-28 的做法）
                    dispatch updateInput({ type: 'composition', value: '今天', timestamps })

input             → ★ 实战轨不依赖此事件做校验（仅用于兜底：非 IME 直接输入的场景，
                       如用户粘贴或英文态直接敲字母 → 走 §3.4 的英文态检测）
```

**类型已预留**：`InputHandler/index.tsx:41-45` 的 `WordCompositionAction` 已定义但**从未被 dispatch**（注释明写 `// composition api is not ready yet`）→ 本次正是让它 ready。

### 3.2 文本 diff 校验

#### 🔴 必须修复的 Bug：现有校验只比对末位字符

`Word/index.tsx:180-181` 只取 `inputWord[inputLength-1]` 与 `displayWord[inputLength-1]` 比对，而 `:86-88` 是**整串追加**。

> **具体后果**：上屏「今天」时，只会拿 `'天'` 与 `displayWord[1]='天'` 比对，**`'今'` 完全未校验**。这是一个静默的正确性 Bug——用户打对了「今」但系统从未检查过。

#### 正确的 diff 算法

```
输入：prevLen（本次上屏前的 inputWord 长度）、newStr（本次上屏文本）、displayWord（目标文本）
1. 对区间 [prevLen, prevLen + newStr.length) 逐字符与 displayWord 同区间比对
2. 全部命中      → 该区间 letterStates 全置 'correct'
3. 首个不命中位  → 该位置置 'wrong'，记录 letterMistake[pos] = 实际字符
                  其后字符置 'normal'（未判定，不允许继续）
4. 长度溢出（上屏字数 > 剩余目标字数）→ 多余部分判错，归类「多打」
5. 漏打：按 CPM 权威口径，「漏打或多打一个字只算一个错误，后面的字不会因此错位」
   → 采用「最长公共前缀 + 单错误容错」而非严格逐位对齐，避免一个漏字导致后续全部错位判错
```

#### 字级 timing 方案（**需 `05` 定稿后择一**）

整串上屏时**没有字级时间戳**（`Word/index.tsx:190` 的 `letterTimeArray.push(Date.now())` 每次 add 只 push 一个）。两个方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **(a) 均摊** | 记录 `compositionend` 时刻，按字符数均摊到每个字 | `timing` 数组长度与字符数一致，**下游 `useWordStats` 的 WPM 计算无需改** | **字级反应时不可信**（均摊是虚构的）→ **必须标注「ime 轨反应时不可用」**（已在 §1.2 精度边界声明） |
| **(b) 段粒度** | 只记录上屏粒度时间戳，DB `timing` 语义改为「每段上屏间隔」 | 数据真实 | `timing` 语义在两个轨道下**不同** → 下游所有消费点（`useWordStats.ts:107-110` 的 WPM 依赖 `Σ timing`）需按 `track` 分叉 |

> **析客建议**：采用 **(b) 段粒度**，并在 `05` 中明确 `timing` 的**双语义**定义。理由：(a) 会制造「看起来精确但实际虚构」的数据，违反 UX-5「诚实高于鼓励」。**此为跨文档待确认项，需数析在 `05` 中定稿。**

### 3.3 全角标点与中英混输（CN-G4）

| 场景 | 目标 | 用户输入 | 判定 | 归类 |
|---|---|---|---|---|
| 全角标点匹配 | `，` | `，` | ✅ 正确 | — |
| **全角/半角不匹配** | `，` | `,` | ❌ 错误 | **「标点格式错误」，不与错字混算** |
| 半角/全角不匹配 | `.`（英文句点） | `。` | ❌ 错误 | 「标点格式错误」 |
| 中英混输 | `我的微信号是Tom_123，请查看2025年Q1报表` | 逐字符 | 英文部分按字符校验，中文部分按字校验，标点按上表 | 分别归类 |

### 3.4 IME 干扰口径与中英文态检测（CN-A2a）

#### 中英文态检测：**Web 无 API 可程序化切换输入法**（TC-4）

只能做「检测 + 提示」，不能做「切换」。检测策略：

| 检测信号 | 判定 | 处置 |
|---|---|---|
| 上屏内容为**纯拉丁字符**（`/^[a-zA-Z0-9]*$/`）而**目标为汉字** | 用户处于**英文态** | 显示非阻塞提示「**请切换到中文输入法**」，**不判错**，**不计入用时**（暂停态），直到用户上屏了 CJK 字符 |
| `compositionstart` 触发 | 用户处于**中文态** | ✅ 正常流程 |
| 对码轨下 `e.key === 'Process'` 或 `compositionstart` 触发 | IME 介入了对码轨（password 失效的兜底场景） | 显示非阻塞提示「请切换到英文输入法」，**不 alert、不判错** |

#### IME 纠错的判定口径（**这是实战轨最需要产品判断的一条**）

| 场景 | 判定 | 计入 | UI 展示 |
|---|---|---|---|
| 用户打错拼音（如 `zhongguo` 打成 `zhonggu`），**输入法纠错后上屏了正确的字** | ✅ **判正确** | **`IME 辅助上屏数` +1** | 与「**零辅助上屏数**」**分开展示**；结算页文案：「本次上屏 320 字，其中 18 字由输入法辅助纠正（5.6%）」 |
| 用户打对拼音，输入法正常上屏 | ✅ 判正确 | `零辅助上屏数` +1 | — |
| 输入法上屏的字**与目标不符** | ❌ 判错 | `wrongCount` +1 | 标红该字 |

**如何判定「是否辅助」**：**无法精确判定**（Web 拿不到输入法的内部纠错状态）。可行的近似口径（需在 `05` 中定义，**UI 须标注「尽力统计，仅供参考」，不得承诺精确**）：
- 近似 1：本次上屏段的**击键数**与该字的**理论码长**不符（如理论 6 键，实际敲了 5 键就上屏了正确字）→ 疑似纠错
- 近似 2：`compositionupdate` 的中间态拼音串与目标字的标准拼音不一致，但 `compositionend` 的结果正确 → 疑似纠错

> **诚实声明（必须写进 UI tooltip）**：「IME 辅助上屏数为**近似统计**。浏览器不暴露输入法的内部纠错状态，我们通过击键数与拼音中间态推断，可能存在误差。」

## 4. 错误处理策略（CN-J2）

### 4.1 三档策略

| 策略 | 行为 | 适用场景 | 与现有行为的关系 |
|---|---|---|---|
| **`rollbackWord`**（整词回滚） | 出错后 300ms 清空整个 `inputWord` 并重置 `letterStates`，需重打整词 | **L0' / L1 / L2 / L3**（字、词、成语） | ✅ **= 现有硬编码行为**（`Word/index.tsx:237-251`），保持向后兼容 |
| **`markOnly`**（仅标错不回滚） | 标红错误位，**允许继续打后续内容**，结算时计入错误 | **L4 / L4C / L5 / L6a / L6b / L6EX / L7**（句子、聊天、诗句、文言短篇、文章、公文、标点专项） | 🆕 新增。**句子级打错一字整句重来是不可接受的** |
| **`rollbackChar`**（单字符回退） | 按 `Backspace` 回退一个字符，可修正 | 用户自选；考试模式下配合「统计退格」（CN-F4） | 🆕 新增。需实现 `WordDeleteAction`（`InputHandler/index.tsx:36-39` **已定义但从未被 dispatch**），且**必须绕开 `isLegal`**（`bannedKeys` 含 Backspace，F2） |

### 4.2 各语料层级默认值（**硬约束，不可由用户误设破坏训练目标**）

| 语料层级 | `inputMode` | 默认 `errorHandlingStrategy` | 理由 |
|---|---|---|---|
| L0' 韵母分组 | code-match | `rollbackWord` | 键位记忆需「错了就重来」形成正确肌肉记忆（金山打字通「错误按键拦截+暂停计时」同一哲学：**防练错肌肉记忆**，与 qwerty-learner「拼错必须重输整词」一致） |
| L1 单字 | code-match | `rollbackWord` | 同上 |
| L2 词组 | code-match | `rollbackWord` | 同上 |
| L3 成语 | code-match | `rollbackWord` | 训练「中途不能停」的连续输入节奏，回滚是节奏训练的一部分 |
| L4 短句 | ime | **`markOnly`** | 句读节奏训练；整句重来会毁掉节奏感 |
| L5 诗句 | ime | **`markOnly`** | 同上；且诗词押韵的「爽快感」被回滚打断会伤害留存（L5 是留存利器） |
| L6a 文言短篇（80-300 字）/ L6b 文章（300-1500 字）/ L6EX 公文 | ime | **`markOnly`** | 长文回滚整段**完全不可接受**（裁定 G-3：L6 已拆 a/b） |
| L7 标点混输 | ime | **`markOnly`** | 标点错误需被单独归类统计，回滚会丢失归因数据 |
| **考试模考（CN-F1）** | ime | **`markOnly` + 可选禁用退格** | 考试计分口径要求「打错/删除重打的字符不计入成绩」，且行为训练要求「**发现某个字不会打或打错了，建议继续往下打，不要回头修改**」 |

### 4.3 设置项 UI

```
【错误处理】
  ○ 整词回滚（打错需重打整词）        推荐用于：字 / 词 / 成语
  ● 仅标错不回滚（可继续往下打）        推荐用于：句子 / 诗句 / 文章      ← 当前语料层级的推荐值高亮
  ○ 单字符回退（可用 Backspace 修正）

  ⓘ 当前词典（L4 短句）的推荐设置是「仅标错不回滚」。
    你可以在这里覆盖它，但请注意：字词级练习用「仅标错」会削弱键位记忆训练效果。

  □ 考试模式：禁用退格（按 Backspace 计入「违规回改」，不回滚）      [默认关闭]
```

> **设计原则**：**默认值由语料层级决定**（`useWordList` 加载词典时按 `level` 设置），用户可覆盖但需看到「推荐值」提示。**不得让用户的误设破坏训练目标**。

> **本表的行序是「文体类型」顺序，不是出题顺序。** 裁定 G-3 明确：「**`level` 只定『文体类型/展示分组』，实际出题顺序由 `codeComplexity`（C1~C6）主导**」。
>
> **反例**：《陋室铭》只有 81 字（**L6a**，本表排在 L6b 之前），但含大量文言虚词与生僻码元，其 `codeComplexity` **很可能高于部分 L6b 白话散文** → **绝不能因为 L6a 编号靠前就把它排在 L6b 之前推给用户**。
>
> **同理 L6EX**：公文虽在本表排在最后，但其中「的/了/是」类高频虚词密度可能**低于**日常散文 → 其 `codeComplexity` 未必更高。
>
> **落地要求（§7 推荐引擎必须实现）**：
> 1. **推荐排序键 = `complexityRank`（0~5 数值教学序），不是 `level`，也不是 `codeComplexity` 字符串**。🔴 **v1.3 更正：`codeComplexity`（C1~C6）的编号序 ≠ 教学序**——真实教学顺序是 `TEACHING_ORDER = ['C1','C4','C2','C3','C5','C6']`（**C4 特殊声母 zh/ch/sh 排第 2**），故字符串比较会得出 `'C4' > 'C2'` 为真、与教学事实相反。排序一律用预计算的 `complexityRank`
> 2. **`level` 只用于 UI 分组展示**（词典选择页的分类、Analysis 页的筛选维度）
> 3. **CI/单测断言**：推荐序列中不得出现「`level` 序号更小但 `complexityRank` 更高」被排在前的情况
> 4. 🔴 **`codeComplexity` 取「教学序 max」而非平均、也非编号数字 max**（裁定 B-3 + v1.3 更正）——
>    - **不取平均**：否则「双拼」这类 C1+C4 的词会被平均成 C2.5，**在用户还没学 zh/ch/sh 特殊声母时就撞上它**
>    - **不取数字 max**：反例是含 **C2+C4** 的词——❌ 数字 max = C4（会让它在用户「学完 C4、未学 C2」时进池 → 撞上真卡点 C2）；✅ **教学序 max = C2**（`complexityRank = 2`）。数析抽验 5 种组合中 **2 种会被数字 max 判错（40%）**，详见 `04` §2.13 的 v1.3 重大更正
>
> **字段来源**：`codeComplexity`（C1~C6 教学难度）、`complexityRank`（= `TEACHING_ORDER.indexOf`）、`codeType`（`fixed`/`zero-initial`/`viu-disambig` 编码类型）均由 `04` v1.3 §3.2 定义、构建期生成。**本文档只消费，不定义**（裁定 B-3 已把两者拆分，§2.3 提示系统的加权项须引 `codeType`）。🔴 **`TEACHING_ORDER` 的唯一真源是 `05` §6.2/§6.6，本文档与 `04` 只引用、不另行定义**（避免第三处常量碰撞，见 `00` §10.8）。

### 7.2 target-key 自适应出题（**keybr 式，最强算法差异化**）

> **keybr 官方披露的算法**（`06`）：按频率降序解锁字母 `E N I T R L S A U O D Y C H G M P B K V W F Z X Q J`，每键有 time-to-type 统计与灰/红/绿指示器，**选出打字速度最差的字母作为 target letter，每一个生成的词都必须包含它**，全绿后解锁下一个；**官方明确承认「旧字母会退化变红」是预期行为**；按音系规则生成伪词（英语中 W 几乎不跟在 Z 后）。

**迁移到中文双拼**：

| keybr 概念 | 中文双拼迁移 |
|---|---|
| 26 字母按频率降序解锁 | **405 音节 / 24 韵母键 + 23 声母键，按真实字频加权解锁** |
| target letter（打字速度最差的字母） | **最弱韵母键**（按反应时 + 正确率综合，口径见 `05`） |
| 每一个生成的词都必须包含 target letter | **每一个练习题都必须包含最弱韵母键** |
| 全绿后解锁下一个 | 该韵母键达双门槛后，target 切换到下一个最弱键 |
| 旧字母退化变红是预期行为 | **旧韵母键退化 = 预期行为，UI 需明示**「这不是退步，是正常的遗忘曲线，练回来就好」（**禁止红色**，UI-HC-3） |
| 按音系规则生成伪词 | **按拼音音节合法性生成**（不生成 `zh` 后接不可能的韵母） |

| **T5** | ⚠️ **这是确定性规则，不是 AI**（NG-11）：「用户只需要『我错在哪给我练那个』，一条确定性统计 + 队列规则即可，不要用 AI 包装」。规则必须可枚举、可单测 |
| **T6** 🆕 | 🔴 **裁定 G-3 + B-3：出题池的准入门槛 = `codeComplexity`（C1~C6），不是 `level`**。target-key 选出最弱韵母键后，**从「用户已解锁的 `codeComplexity` 档位内」筛含该键的词条**，不得跨越用户尚未学到的 C 档（否则「双拼」这类 C4 词会在用户还没学 zh/ch/sh 时撞上）。**`level` 在此只用于 UI 分组，不参与准入判定**。<br>🔴 **v1.3 硬约束：准入与排序的比较必须用数值字段 `complexityRank`（0~5），绝不能用 `codeComplexity` 字符串直接比较**。因为 `TEACHING_ORDER = ['C1','C4','C2','C3','C5','C6']` 中 **C4 排第 2、C2 排第 3**，而字符串比较会得出 `'C4' > 'C2'` 为真 → **判定与教学事实相反**。「用户已解锁的档位」也必须按 `complexityRank` 阈值表达（`unit.complexityRank <= userUnlockedRank`），不得写成 `unit.codeComplexity <= 'C3'` |
| **T7** 🆕 | 🔴 **`codeComplexity` 词条级取「教学序 max」**（裁定 B-3 + 数析 v1.3 更正）：一个词只要含一个 C5 零声母字，整词就是 C5，必须等用户解锁到 C5 才进池。**这保证不变式「词条难度 ≥ 其所有构成码元的已学状态」**。字段与 `complexityRank` 由 `04` §3.2 构建期生成，本文档只消费。<br>🔴 **必须用教学序而非编号数字序取 max**：`TEACHING_ORDER = ['C1','C4','C2','C3','C5','C6']`（**C4 特殊声母 zh/ch/sh 排第 2**，因它是双拼与全拼的首要差异点、小鹤官方「一小时记键位」的主体）。反例：某词含 **C2 + C4** 时，❌ 数字 max = C4（会让它在用户「学完 C4、未学 C2」时进池 → 撞上真卡点 C2）；✅ **教学序 max = C2**（`complexityRank = 2`）。数析抽验 5 种组合中 **2 种会被数字 max 判错（40%）**，后果正是本条要避免的「词条过早进入出题池」。详见 `04` §2.13 的 v1.3 重大更正与 CI 断言 Q-16 |

### 7.3 四向单键专项训练（**竞品 P0 必采**）

> 来源：`shuangpin-practice` 的「键位记忆训练」。**设计理由（原文）**：「完整音节练习里一个字的错误**分不清是声母想不起来还是韵母记错了**，这个模式把两部分拆开。」

| 方向 | 题面 | 用户操作 | 训练目标 |
|---|---|---|---|
| **① 韵母 → 键** | 显示 `ing` | 按对应键（`K`） | 韵母键位记忆（**双拼的核心，官方原话「你要学习的部分主要就是韵母键位被设定到哪个键上」**） |
| **② 声母 → 键** | 显示 `zh` | 按对应键（`V`） | 特殊声母键位记忆（zh/ch/sh → V/I/U） |
| **③ 音节 → 声母键** | 显示 `zhong` | **只按第 1 键**（`V`） | 拆分能力：从音节中提取声母 |
| **④ 音节 → 韵母键** | 显示 `zhong` | **只按第 2 键**（`S`） | 拆分能力：从音节中提取韵母 |

**交互规格**：四向可在设置页单独开关；每个方向独立统计正确率与反应时；**③④ 方向的错误可精确归因到「声母问题」或「韵母问题」**，直接喂给 CN-C7 易错音归因与 CN-E3 韵母热力图。

### 7.4 四种出题模式（**竞品必采，来自 `Return7-T/Shuang`**）

| 模式 | 说明 | 适用 |
|---|---|---|
| **全部随机** | 从当前解锁范围随机出题 | 日常练习（**默认**，防伪掌握 I4） |
| **全部顺序** | 按新华字典序出题 | 系统性过一遍（**不推荐日常使用**，会导致伪掌握） |
| **困难随机** | **只出韵母需要转换的字**（即韵母不在同名字母键上的字，如 `uang→L`；排除 `a→A`、`e→E`、`i→I`、`o→O`、`u→U` 这类「不需要记」的） | 高效练习（排除已天然掌握的项） |
| **无拼音** | **移除多音字与生僻字** | 数据质量兜底（Shuang 的做法；**「嗯」这类多口径字应从此模式排除**，A1 §3.5） |

### 11.3 全站 `alert()` 替换清单（A11Y-5，**这既是 a11y 要求也是功能要求**）

> **病因**：原生 `alert()` **阻塞 JS 事件循环**。阻塞期间 keydown 事件丢失、焦点状态错乱 → 这正是 Issue #744「关闭 alert 后在 Pause 界面按 Shift 无法切换中英文」的病因。

| # | 位置 | 现有 | 改为 |
|---|---|---|---|
| 1 | `KeyEventHandler/index.tsx:14-17` | `alert('您正在使用输入法，请关闭输入法。')` | 非阻塞弹层（fork 用 `sweetalert` 的 `swal`） |
| 2 | `TextAreaHandler/index.tsx:48-50` | `onCompositionStart={() => alert(...)}` | **实战轨：必须删除**；对码轨：改为非阻塞弹层（`type="password"` 后基本不触发） |
| 3 | `Typing/index.tsx:40-49` | 移动端提示 `alert` | 非阻塞弹层 |

**⚠️ 两个改动缺一不可，机理不同**（Issue #744 的已验证解法）：
- `type="password"`：浏览器/OS 层强制关闭 IME（**解决「IME 干扰」**）
- `alert → swal`：解除事件循环阻塞（**解决「关闭 alert 后 Shift 切换失效」**）

### 12.2 移动端定位（**诚实表述，不得过度承诺**）

| 项 | 结论 |
|---|---|
| **技术事实** | 🔴 **对码轨在移动端浏览器技术上几乎不成立**——软键盘拿不到原始 `keydown`（TC-5）；`type="password"` 在移动端会调出不同的虚拟键盘 |

| **不做的（NG-10）** | ❌ 移动端专项优化 ❌ 移动端软键盘适配 ❌ 移动端手势操作 |

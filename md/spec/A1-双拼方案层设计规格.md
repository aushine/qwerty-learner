## 一、双拼方案层的产品定位

### 1.1 为什么需要独立的「方案层」

竞品调研结论（详见 `06-竞品分析与市场定位.md`）：
- **多方案支持是刚需，不是加分项**。开源项目 `Return7-T/Shuang` 支持 **20+ 种方案**（自然码/搜狗/微软/小鹤/智能ABC/拼音加加/紫光/国标/小浪/大牛/蓝天/键道3/键道6/星空/开源小鹳/小月/韵标块拼/C双拼/白云），证明该抽象层可行且社区有需求。
- **方案迁移是真实行为**。V2EX 一手案例：用户学完小鹤两周后「**放弃了小鹤键位，花了一周时间切到微软键位上。因为当时微软双拼键位的通用性更强一点，iOS 和 macOS Gboard 直接支持，开箱即用**」。
- **只支持单一方案是现有开源竞品的最大限制**。`z1803406304/shuangpin-practice`（功能最完整的开源双拼练习器，2026-09 首发）作者自述已知限制第一条即为：「**只实现了小鹤双拼一种方案**。加方案 = 在 `core/schemes/` 加一个文件 + 注册，但要注意 `initialsOfKey()` 目前写在 `xiaohe.ts` 里，**加方案时得按方案拆开**」。
  → **这是我们要在接口设计阶段就规避的坑**：方案文件必须自包含，不得把方案特有逻辑泄漏到共享层。

### 1.2 方案层的职责边界

| 属于方案层 | 不属于方案层 |
|---|---|
| 韵母 → 键 的映射（`keyMap`） | 语料内容与分级（→ 04 文档） |
| 声母 → 键 的映射（含 zh/ch/sh 特殊键） | 章节进度与关卡通过条件（→ 04 文档） |
| 零声母音节补齐规则（`zeroMap`） | 指标计算（击键/码长/CPM，→ 05 文档） |
| ü / üe / üan / ün 的书写归一规则 | 键位图 UI 渲染样式（→ 02 文档） |
| 隔音符处理（若有） | 游戏化机制（→ 09 文档） |
| 方案元信息（ID、名称、跨平台支持度、社区活跃度） | 系统输入法联动（我方不联动，见 §5.2） |
| **音节 → 应该按哪两个物理键（编码映射）** | **⭐ 字符实际形态判定：全角/半角、繁简、异体字（→ 走 ime 实战轨，见 §5.2.1）** |

> **⭐ 职责边界一句话（主理人 2026-10-17 裁定 X-A2-2）**：**方案层只管编码映射，不管字符形态判定。** 编码映射走 code-match 对码轨（`KeyboardEvent.code` 物理键位），字符形态（全角/半角、繁简、异体字）走 ime 实战轨（`compositionend` 的 `e.data`）。两轨天然隔离——`ing` 这类编码校验语义只存在于对码轨，L7 恒走 ime 实战轨，**因此不需要「方案层与 L7 做互斥」**。详见 §5.2.1。

> **关键设计点**：`V`、`I`、`U` 三键**同时承载声母与韵母**（V = zh + ui + ü；I = ch + i；U = sh + u）。**双拼通过键位顺序消除歧义**：第一键位置的 V/I/U 解释为声母，第二键位置解释为韵母。
> S2 原文：「V 作为第一键可表示 zh；作为第二键可表示 ui 或 ü。**双拼固定的键位顺序会消除歧义，不需要额外选择。**」
> → **判定引擎必须按位置解释，不能用单一「键→音」反查表**。这是实现层最容易出错的点。

## 三、零声母与特殊音节规则

### 3.1 小鹤官方零声母方案（S4，原文转述）

> 「**=零声母方案** 指全拼中无声母的韵母音节在双拼中的处理方案，用来充当其声母的字母即零声母。**以韵母首字母为零声母**，即把韵母的首字母当作声母：
> - **单字母韵母**，零声母 + 韵母所在键，如：**啊=aa 哦=oo 额=ee**
> - **双字母韵母**，零声母 + **韵母末字母**，如：**爱=ai 恩=en 欧=ou**
> - **三字母韵母**，零声母 + **韵母所在键**，如：**昂=ah**
> 即：**双字母音节保持全拼方式，一三字母音节为首字母加韵母所在键**」

S2 的表述与此一致：「本站采用小鹤常见的两键补齐规则：**单字母韵母重复输入；两字母音节保留全拼；ang、eng 这类更长的音节用首字母加该韵母的映射键**。」

S3（ulpb）零声母表 DOM 一手抓取，**12 项**：
`a→aa`、`ai→ai`、`an→an`、`ang→ah`、`ao→ao`、`e→ee`、`ei→ei`、`en→en`、`eng→eg`、`er→er`、`o→oo`、`ou→ou`

### 3.2 ✅ 重大信源冲突已定级：零声母双字母音节的第二键（C-4）

> **⭐ 推演得到的关键结构化事实（初稿完全未识别）**：**只有 6 个「双字母零声母音节」（`ai`/`ei`/`ao`/`ou`/`an`/`en`）存在双口径**，其余零声母音节（单字母 `a`/`o`/`e`、三字母 `ang`/`eng`、以及 `er`）**都是单值**。原因是官方对前者用 `derive`（L57）、对后者用 `xform`（L58）——**两个算子的选择本身就是官方的口径声明**。这使兼容逻辑的爆炸半径从「全部零声母音节」收敛到「6 个音节 × 2 口径 = 12 个用例」。

**冲突根因分析（⭐ 2026-10-17 一手取证后重大更新）**：

> **本节初稿基于 rime-ice 混输变体推测，现已用 Rime 官方 `double_pinyin_flypy.schema.yaml`（commit `01a1328`, v0.18）一手规则链核对，结论有实质变化。**

- **口径 α** 来自小鹤官方文档、ulpb 键位图零声母表、shuangpin.xyz、纸砚 zeroMap 格式（**四者互相独立且一致**），代表**飞扬版小鹤 / 主流商业输入法（搜狗、QQ、百度内置小鹤方案）的实际行为**。
- **⭐ 官方规则链的关键事实（行级证据，S1 commit `01a1328`）**：
  ```yaml
  # double_pinyin_flypy.schema.yaml, speller/algebra
  L56:  - derive/^([jqxy])u$/$1v/          # ü 归一：ju→jv（derive）
  L57:  - derive/^([aoe])([ioun])$/$1$1$2/  # ⭐ 零声母【双字母】：ai→aai（derive）
  L58:  - xform/^([aoe])(ng)?$/$1$1$2/      # 零声母【单/三字母】：ang→aang（xform）
  L71:  - xform/(.)ai$/$1D/                 # ai→D（xform，需 ai 前有一字符，故只命中 aai）
  ```
  **⭐⭐ 决定性发现**：官方对**零声母双字母音节**用的是 **`derive`（第 57 行），不是 `xform`**。`derive` 是「**额外派生，两种都接受**」，`xform` 才是「强制变形，只接受一种」。
  - 推导 `ai`（爱）：L57 `derive` 使 `ai` **同时保留 `ai` 并派生出 `aai`**；随后 L71 `xform/(.)ai$/$1D/` **只命中 `aai`**（该正则要求 `ai` 前有一个字符，故 2 字母的 `ai` 不匹配）→ `aD` → `xlit` → `ad`。**因为 L57 是 derive，原始的 `ai` 也仍然有效** → **`爱` 的最终可接受编码 = {`AI`（原样保留）, `AD`（派生后变形）} 两者皆可**（模拟器推演输出 `AD,AI`，逐字吻合）。
  - 而单/三字母（L58 `xform`）是强制变形：`ang`→`aang`→`aH`→`ah`，**只接受 `AH`**；`er` 因不匹配任何规则而**原样穿透**，只接受 `ER`。

- **⭐ 结论修正（C-4 从「冲突待核对」升级为「已由官方规则链定级」）**：
  - **这不是 rime-ice 变体独有的混输行为，而是 Rime 官方版本 v0.18 的既定设计**：官方用 `derive` 处理零声母双字母，**本身就同时接受口径 α（`AI`）与口径 β（`AD`）**。
  - **我方 §3.2 建议的「双口径兼容判定 + α 为主口径」策略，与 Rime 官方实现完全一致** —— 从「产品层面的妥协」升级为「与权威实现同源的正确设计」。**这条决策现在有 A 级一手证据支撑，不再是权宜之计。**
  - **单/三字母零声母（a/o/e/ang/eng/er）无口径分歧**（官方用 xform 强制变形或原样穿透），只有 `ai/ei/ao/ou/an/en` 这 6 个双字母音节存在双口径。
  - ⚠️ **C-4 唯一残留（降为「实施后验证项」，不阻塞）**：**飞扬版小鹤 / 搜狗 / QQ 等商业输入法**是否也接受双口径，还是只认 α。Rime 官方接受双口径不代表所有输入法都接受。**但这不影响我方决策**：我方判定引擎接受双口径（α 为主、β 兼容通过），是**所有输入法环境的最大公约数**，无论用户用哪种都不会误判。→ **C-4「阻塞」状态关闭。**

**⭐ 产品决策（已由取证支撑，从「建议」升级为「结论」）：双口径兼容判定（两者都判对）**

理由：
1. **用户系统输入法环境不确定**。用户可能用飞扬版小鹤（口径 α）、搜狗内置小鹤（口径 α）、Rime double_pinyin_flypy（**官方 α+β 双收**）、雾凇拼音（混输，两者都收）。**练习器若只认一种，会与用户日常输入习惯冲突**，而巧手打字通的专业排查文已明确「**练习工具与系统输入法方案不一致**」是双拼练习挫败的第一大故障源，且「**不可以混用方案练习**」。
2. **零声母音节在真实语料中占比不低**（"爱、安、昂、欧、恩、啊、哦、饿、二"均为高频字），若判错会严重污染准确率与错键热力图数据。
3. **实现成本低**：`zeroMap` 中为每个双字母零声母音节配置一个 `accepted: string[]` 数组即可（且该数组语义**已被 §5.2.2 提升为全局统一要求**，非零声母专用）。
4. **教学价值**：可在键位图提示中同时显示两种，并注明「你的输入法可能使用其中一种」，顺带教育用户去核对自己的输入法配置。

**但必须满足三个附加要求**：
- **统计需分离**：若用户对同一题在不同轮次使用不同口径，应记录其**主用口径**（用于后续个性化出题），避免数据混淆。
- **默认值需选定**：结算与「独立正确率」计算时以**口径 α 为主口径**（四信源支持 + 覆盖主流商业输入法），口径 β 记为「兼容通过」而非「主口径通过」。**此项需与数析（05 文档）确认统计口径。**
- **⭐ 新增（取证要求）：兼容范围必须严格限定在这 6 个双字母音节**。单/三字母零声母音节**禁止**配置双口径——那会把官方 `xform` 的唯一编码语义破坏掉，属实现 bug（对应 §5.3 第 4 层测试族 4-B 的反向断言）。

**✅ C-4 核对状态更新（2026-10-17）**：Rime `rime-double-pinyin` 官方 `double_pinyin_flypy.schema.yaml`（**非** rime-ice 混输变体）**已完成一手核对**，取证方式与行级证据见 §3.4。**飞扬版小鹤 / 搜狗（小鹤方案）两环境的实测已排入 A3 文档 S8**（主理人裁定），**不阻塞 spec 定稿与 P0 实施**。

#### 3.4.2 官方版 vs 初稿误引的 rime-ice 混输变体：差异对照

| 维度 | **官方 `rime-double-pinyin`**（本轮取证） | rime-ice 混输变体（初稿误引，已废弃留档） |

> **⚠️ 为什么这个差异对本项目至关重要**：混输变体的全 `derive` 设计意味着「同一音节有两条合法编码」（全拼码 + 双拼码），**判定引擎无法据此判断用户是否在正确使用双拼**。我方判定必须建立在**官方 `xform` 的强制变形语义**上——每个音节只有唯一双拼码（唯一例外是 L57 零声母双字母的 α/β 双口径）。
> → **产品结论**：我方 `{keyMap, zeroMap}` 应**照官方 `xform` 语义建模为 1:1 强制映射**，仅在 `zeroMap` 的双字母条目上显式声明 α/β 双口径（见 §5.2、§6.2）。**不得照搬 rime-ice 混输变体。**

**规则顺序有意义**（官方原文顺序即为证据）：
1. **擦除无效模式**：`erase/^xx$/`（L55，官方确为首行——初稿的猜测被证实）
2. **ü 归一**：`derive/^([jqxy])u$/$1v/`（L56）—— 必须在韵母映射之前，否则 `[uv]e$/T/`（L62）无法同时覆盖 `ue` 与 `üe`
3. **零声母补键**：L57（双字母 `derive`）→ L58（单/三字母 `xform`）—— 顺序不可颠倒，否则 L58 会把 L57 已派生的结果再次变形
4. **韵母 → 大写中间符号**：L59-L63、L67-L83
5. **声母 zh/ch/sh → 大写中间符号**：L64-L66
6. **中间符号 → 实际按键**：`xlit`（L84，规则链最后一步）

> **⚠️ 实施警示**：Rime 用户若在 `speller/algebra` 中**添加模糊音规则**（如 `derive/^([zcs])h/$1/` 使 zh/ch/sh 与 z/c/s 互转、`derive/in$/ing/` 前后鼻音互转），**必须放在双拼转换规则之前，顺序错误会导致功能失效**（GitCode 博客与 scutlmg.github.io 两份 Rime 配置文档一致指出）。
> → **产品启示**：我方判定引擎**不接受用户自定义模糊音**（保持标准编码纯净），这与巧手排查文的建议一致（「关闭全拼兼容、自定义辅码，仅保留标准两键双拼规则」）。若未来要支持模糊音练习，应作为**独立的「模糊音矫正」练习模式**，不污染主判定链。

#### 4.5.1 ✅ C-6 关闭：`üe` 键位冲突的权威答案

初稿记录的冲突是「百度百科：`ue=T`、`ve/ui=V`（两者分离）」vs「CSDN：`T=ue`、`V=zh,ui,ue`（ue 也在 V）」。**官方 schema 显示两个信源都只对了一半，真相是第三条路径：**

```yaml
# double_pinyin_mspy.schema.yaml
L62:    - xform/[uv]e$/T/     # ue 与 üe（词典层写作 ve）都被强制变形到 T
L81:    - xform/ui$/V/        # ui → V
L82:    - derive/T$/V/        # ⭐ 关键：额外派生「T 结尾 → 也接受 V」
```

**定论（A 级）：**
1. **`üe` 的规范键是 `T`**（L62 的 `[uv]e` 字符类同时匹配 `ue` 与 `ve`，即 `ue`/`üe` **共用 T**，与小鹤同构）。→ **百度百科的「üe→V」是错的**（它把 L82 的派生规则误读为主规则）。
2. **但 `V` 也被官方接受**——因为 **L82 `derive/T$/V/` 是 `derive`（额外派生，保留原式）**，它在 L62 之后执行，把所有已变形为 `T` 结尾的编码**再派生一份 `V` 结尾的等价编码**。→ **CSDN 的「V 也有 ue」是对的，但没说明这是派生兼容而非主键位。**
3. **推演验证**：`xue`→{**`XT`**（主）, **`XV`**（派生）}（见 §4.2.1 矩阵），与上述分析完全吻合。

**→ 实施决策（与小鹤 C-4 同构，可复用同一套判定机制）：**

| 项 | 决策 |
|---|---|
| 微软 `üe` 的**主键位**（用于键位图渲染、教学提示、错误归因） | **`T`** |
| 判定引擎**是否接受 `V`** | **接受**（因官方 `derive/T$/V/` 明确支持） |
| 计分口径 | 打 `T` 与打 `V` **均判正确**；但**统计「规范率」**，在练习报告中标注「本次 N 处使用了兼容键位 V，规范键位为 T」 |
| 数据结构 | 微软方案的 `keyMap` 中 `üe` 条目必须是**数组** `["T","V"]`（首元素为主键位）——**这与 §4.2.1 C-12 的「集合语义」要求一致，可由同一个数据结构承载** |

> **⭐ 架构收益**：C-4（小鹤零声母 α/β）、C-6（微软 üe 的 T/V）、C-12（微软零声母三值）三个问题**本质是同一件事**——**官方 Rime 用 `derive` 表达「一个音节有多个合法编码」**。因此方案层的数据结构只需**统一支持「音节 → 编码集合，含主键位标记」**，即可一次性覆盖全部三个问题，无需为每个方案写特例。
> → **这是对 §5.2 结论的直接强化**：`{keyMap, zeroMap}` 的值类型应为 `string[]`（首元素 = 主键位/主口径），而非 `string`。

> **S5 的重要工程警示（原文）**：「微软原生双拼是三套方案中**唯一使用标点符号（分号）作为韵母键**的方案，在**网页编辑器、远程桌面、带快捷键的软件中，容易出现按键拦截、输入失效问题，需要单独适配环境**。」
> ⚠️ **取证修正**：官方六方案中**微软与 四通 两个方案使用分号键**（`alphabet` 含 `;`，且均有 `xform/ing$/;/`：微软 L85、四通 L78），S5「三套方案中唯一」的说法在其对比范围内成立，但不是全生态唯一。
> → **产品启示（P0 级，取证后更强）**：我方走 `KeyboardEvent.code` 物理键位捕获架构（见 §5.2），**`Semicolon` 的 `event.code` 是稳定的**，不受浏览器/输入法/快捷键拦截影响，**恰好规避了分号键方案的最大工程风险**。这是该架构决策的又一有力论据——**且因 四通 也用分号键，这个优势覆盖的方案比初稿估计的更多**。

## 五、判定引擎表达方式：结论建议

### 5.1 三种候选方案对比

| 方案 | 描述 | 优点 | 缺点 | 代表实现 |
|---|---|---|---|---|
| **A. 正则代数链** | 复刻 Rime `speller/algebra` 的 `derive/xform/xlit` 规则链，运行时对拼音串做正则变换 | 与 Rime 生态同源，**可直接移植其配置做交叉验证**；规则紧凑 | 运行时正则回溯开销；**规则顺序敏感，易错且难调试**；可读性差，社区贡献门槛高；键位写错难以肉眼发现 | Rime |
| **B. 声明式映射表** | `{ 韵母: 键 }` + `{ 零声母音节: 编码[] }` 的字典，运行时按音节拆分后查表 | **直观、可读、可 diff review**；易扩展新方案；易写全量单测 | 需要枚举（但音节总数有限，仅 405 个）；需自行实现音节拆分 | `shuangpin-practice` 的 `core/schemes/xiaohe.ts` |
| **C. 音节全量静态表** | 构建期把 **405 个音节 → 2 键编码** 全部枚举为静态表，运行时 O(1) 查表 | **运行时最快**（O(1)，无正则、无拆分）；**可全量回归单测**；结果确定性强 | 表体积较大（但 405 条极小）；多音字需在读音层解决而非编码层 | `shuangpin-practice`（「405 音节按真实字频加权」+「编码器含 405 音节全量回归」） |

### 5.2 ⭐ 结论建议：B + C 组合（映射表为唯一事实源，静态音节表为运行期产物）

**推荐架构**：

```
[声明式方案配置]           [构建期生成]              [运行期]
{keyMap, zeroMap}   ──→   405 音节 → 2键编码表   ──→  O(1) 查表判定
   唯一事实源                  产物，不手改                无正则、无拆分
   （人工可 review）                                       （确定性、可测）
```

**理由**：
1. **可读性是安全属性**。键位表写错会让用户练错肌肉记忆（`shuangpin-practice` 作者原话：「双拼练习器最容易出错的地方是『键位表写错』，而写错了用户会跟着练错。所以这个项目的**正确性不靠肉眼核对，靠三层验证**」）。声明式 `keyMap` 可被人工逐行 review、可被 diff、可被社区 PR 贡献，这是正则链做不到的。
2. **运行期 O(1) 且确定性强**。打字练习对按键延迟极敏感（击键 10/秒 = 100ms/键），不能有正则回溯抖动。
3. **可全量回归单测**。405 音节全量断言，任何键位改动都会立即被单测捕获。

#### 5.2.1 ⭐ 方案层的职责边界（主理人 2026-10-17 裁定 X-A2-2，必须遵守）

> **方案层只管编码映射，不管字符形态判定。**

这一句是本节最重要的一行，用于收口 A2 §2.1c 提出的「L7 全角/半角与 `event.code` 架构不兼容」冲突。裁定明确：**不需要「方案层与 L7 做互斥」**，因为两者天然隔离在不同轨道上。

| 判定对象 | 走哪一轨 | 数据来源 | 谁负责 |
|---|---|---|---|
| **编码映射**（音节 → 应该按哪两个物理键） | **code-match 对码轨**（L0~L3） | `KeyboardEvent.code`（物理键位） | **方案层**（本文档 §2~§4 的 `keyMap`/`zeroMap`） |
| **字符实际形态**（全角/半角、繁简、异体字、标点样式） | **ime 实战轨**（L4~L7） | `compositionend` 事件的 `e.data` | **语料层 + 实战轨判定器**（A2 与 02 负责，不在方案层） |

**为什么天然隔离（裁定依据，写入 spec 供后续实施者理解）：**
- `ing` 这类**编码校验语义**只存在于 **code-match 对码轨**——它校验的是「用户是否按对了键」，与最终上屏字符长什么样无关；
- **L7 恒走 ime 实战轨**，判定的是「上屏字符是否与目标文本一致」，此时**编码已被输入法内部消化**，方案层根本不参与；
- 因此**同一个 `ing` 不会同时出现在两轨的判定逻辑里**，无需任何互斥开关或条件分支。

**→ 实施纪律（两条）：**
1. 方案层的配置与代码**禁止**出现全角/半角、繁简、异体字相关的任何字段或分支；若发现需要，说明职责划分错了，应退回实战轨处理。
2. 实战轨判定器**禁止**反查方案层的 `keyMap`；它只比对 `e.data` 与目标字符串。

#### 5.2.2 ⭐ `keyMap`/`zeroMap` 的值类型必须是数组（本轮取证得出的强制要求）

初稿建议 `zeroMap` 的值用数组以承载「双口径」，但把 `keyMap` 视为单值。**本轮官方 schema 取证证明这个区分是错的——三个独立问题都要求数组语义：**

| 问题 | 现象 | 官方证据 |
|---|---|---|
| **C-4**（小鹤零声母 α/β） | `ai` → {`AI`, `AD`} 两个合法编码 | flypy L57 `derive`（保留原式 + 追加派生式） |
| **C-6**（微软 `üe` T/V） | `xue` → {`XT`, `XV`} 两个合法编码 | mspy L82 `derive/T$/V/`（在 L62 `xform/[uv]e$/T/` 之后追加） |
| **C-12**（微软零声母多值） | `ai` → {`OL`, `AL`}、`er` → {`ER`, `OR`} | mspy L57 `derive` + L58 `xform` 双规则叠加 |

**统一结论**：官方 Rime 用 **`derive` 算子表达「一个音节有多个合法编码」**，而 `xform` 表达「唯一编码」。因此方案层数据结构应统一为：

- **`keyMap` 与 `zeroMap` 的值类型均为 `string[]`（数组），首元素约定为「主键位 / 主口径」**；
- 单值情形（绝大多数）写成单元素数组即可，**数组语义向下兼容单值**，无需为每个方案写特例；
- **主键位（首元素）**用于三件事：① 键位图渲染与教学提示；② 错误归因（用户打错时提示的是主键位）；③ 「规范率」统计（打中非首元素的合法编码时，判对但计入规范率折损）。

**→ 计分口径（与 09 §5 的准确率优先原则一致）**：命中数组内**任一**编码 = **正确**；命中**非首元素** = 额外累计一条「使用了兼容键位」的轻量提示（不扣分、不弹窗打断，只在结算页汇总）。**绝不可把兼容键位判为错误**——否则用户在自己的输入法环境下会被系统性误判，这正是 §3.2 指出的「练习工具与系统输入法不一致」第一大故障源。

4. **Rime algebra 仅作开发期交叉验证**，不进产物 —— 这与 `shuangpin-practice` 对小鹤官方码表的处理方式完全一致（「码表只用于开发期的交叉验证脚本，码表数据没有进入本仓库的产物」）。
5. **音节拆分放在构建期**，运行期不需要处理多音字/隔音符，大幅降低运行时复杂度与 bug 面。

**⭐ 与 P0-1 架构决策的强关联**：
判定引擎的输入不是「文本框里的字符串」，而是 **`KeyboardEvent.code` 物理键位序列**。因此：
- 判定方向是 **「用户按键序列 → 与期望编码比对」**，而非「拼音串 → 编码」
- **不需要 IME composition 事件**，彻底规避 monkeytype Issue #4673 的死穴（该 Issue 状态为 closed as not planned，用户实测「This makes typing in Chinese basically impossible on Monkeytype」）
- **键盘布局无关**（`event.code` 是物理键位，Dvorak/Colemak 用户也能练 QWERTY 双拼键位）—— `shuangpin-practice` 已验证此做法
- **规避微软双拼分号键拦截风险**（见 §4.5）
- 移动端可降级为「点键位图」产生等价的 `code` 事件

**接受的字符集**：仅 `KeyA`~`KeyZ` 与 `Semicolon`（对应 Shuang 项目「输入内容只能为字母或半角分号 `;`」的约定）。

### 5.3 必须建立的三层质量验证（照抄 `shuangpin-practice` 方法论）

| 层次 | 做法 | 该项目实测结果 |
|---|---|---|
| **单元测试** | 编码器（含 **405 音节全量回归**）、提示策略、统计、历史、题库与语料质量、出题器、状态机 | `npm test` **81/81** |
| **交叉验证** | 下载**官方码表**，对每个单字取官方编码前两位与编码器输出**逐字比对** | **7674/7701 一致（99.649%）**；27 处不一致经解码确认**全部是生僻多音字的读音取舍差异**（例：蔈，官方 `bn`→biao，编码器 `pn`→piao），**不是编码错误** |
| **端到端** | 用无头浏览器在真 `file://` 下跑完整流程（渲染、按键、暂停、刷新持久化、按需加载） | **19/19** |

**⭐ 我方额外应建立的第 4 层（竞品都没有）**：**多合法编码（集合语义）兼容测试**。

初稿写的是「为 12 个零声母音节各建 α/β 两组用例」。**本轮取证后范围大幅收敛并更精确**：

| 测试族 | 范围（取证确定） | 断言 |
|---|---|---|
| **4-A 零声母双口径** | **仅 6 个双字母零声母音节**：`ai`/`ei`/`ao`/`ou`/`an`/`en`（因 flypy L57 用 `derive`） | α 与 β **均判正确**；主口径记为 α；打 β 时累计「兼容键位」计数 |
| **4-B 零声母单值严格性** | 其余零声母音节：`a`/`o`/`e`/`ang`/`eng`/`er`（因 L58 用 `xform`，**唯一编码**） | **必须严格单值判定**，接受 β 即为 bug（回归防线） |

## 六、多方案可插拔扩展接口设计（`{keyMap, zeroMap}` 格式借鉴说明）

> **边界声明**：本节只给出**方案层的概念模型与借鉴来源**，**不设计 JSON schema、不定义 TypeScript interface**（那属于 `03-模块与架构设计.md`，析客负责）。

### 6.1 四个竞品的扩展机制对比与借鉴

> ⚠️ **重要更正（信源溯源）**：`{keyMap, zeroMap}` 这一命名**并非我方原创，也不是从 shuangpin-practice 借鉴**，其**原始出处是纸砚（`Yidadaa/shuangpin`，507 stars）**。其 README「如何贡献一个新的双拼方案？」一节给出了完整的配置文件格式。由于纸砚是 **MIT + Anti-996 双许可、与本项目 GPL-3.0 不兼容**，**其配置数据不得复制**，我方只借鉴其**格式思想**并自行实现（思想/表达二分法：字段命名与组织思路属思想层面，具体数据属表达层面）。详见 A2 §4.3。

**纸砚的方案配置格式原文（README 一手）**：
```
{
  "双拼名称": {
    "keyMap": {              // 按键配置
      "q/iu/q",              // 键盘按键/韵母/声母
      "t/ue,ve/t",            // 如果有多个韵母,请使用英文逗号隔开
    },
    "zeroMap": {             // 零声母配置
      "aa/a",                // 双拼/拼音
    }
  }
}
```
纸砚的贡献方式：**「直接编辑这个文件，仿照已有的配置格式新增即可，编辑完毕后发起 Pull Request，请在 Pull Request 中说明方案来源。」** —— **单文件 + 单步 PR**，贡献门槛全场最低。
纸砚另有两条实现约束值得注意：① 「多音字列表过长时会进行截断处理，此时虽然提示列表中没有展示，但依然可以正常判定」；② **「自定义双拼模式下，若出现一对多的双拼映射关系（单个双拼输入对应多个可能拼音），会导致重码率上升，所以并未对此类方案做兼容」**。

**四竞品扩展机制横向对比**：

| 项目 | 扩展方式 | 可借鉴点 | 需规避的坑 |
|---|---|---|---|
| **纸砚**（`Yidadaa/shuangpin`，507★） | ⭐ **`{keyMap, zeroMap}` 声明式配置，单文件编辑 + 单步 PR**；另有「设置 → 当前模式 → 新增双拼」支持用户本地自定义方案 | ① **贡献门槛最低**（改一个文件、发一个 PR，README 要求「说明方案来源」—— 这一条很关键，可追溯数据出处）；② **`keyMap` 用 `"键/韵母/声母"` 三元组统一表达**，把「一键多韵母」与「同键承载声母+韵母」两种情形合并进一个字段（如 `"t/ue,ve/t"`、`"q/iu/q"`），设计优雅；③ **同时支持用户本地自定义方案**（不必发 PR 也能练自己的方案）；④ `zeroMap` 用 `"双拼/拼音"` 格式，天然可反查 | ⚠️ **许可不兼容（MIT + Anti-996 vs 我方 GPL-3.0），数据与代码不得复制**；`keyMap` 用斜杠分隔字符串表达，**解析成本高、易写错、难做类型校验**（应改为结构化对象/数组）；「一对多映射不兼容」是明确的功能限制 |

### 6.2 `{keyMap, zeroMap}` 概念模型建议（融合纸砚格式 + 修正其缺陷）

**一个方案 = 一份自包含声明**，概念上包含以下六块（命名与具体 schema 由 `03-模块与架构设计.md` 定）：

| 概念字段 | 内容 | 借鉴来源 | 我方修正 |
|---|---|---|---|
| `keyMap` | **韵母/声母 → 键** 的映射 | 纸砚的 `"键/韵母/声母"` 三元组思想 | ⚠️ **改为结构化表达**（对象或数组），不用斜杠分隔字符串；⭐ **值类型为 `string[]`，首元素为主键位**（取证要求，见 §5.2.2 与下方要求 3） |
| `zeroMap` | **零声母音节 → 可接受编码列表** | 纸砚的 `"双拼/拼音"` 思想 | ⭐ **值必须支持多口径数组**（`ai: ["AI", "AD"]`），承载 §3.2 的信源冲突兼容 —— 这是纸砚未做的（其格式 `"aa/a"` 是单值） |
| `zeroMode` | **零声母范式标记**（二选一）：`repeat-initial`（首字母重复）/ `o-prefix`（O 前缀补齐） | ⭐ **本轮取证原创**（六大官方方案归纳） | ⭐ 取证发现零声母只有两种家族（§4.1.1 结论 2），**`zeroMode` 让新增方案无需手写 12 条零声母映射，只选一个范式 + 极少数例外**，扩展成本从「N 种方案」降到「2 种范式」 |
| `initialMap` | **声母 → 键**（含 zh/ch/sh 特殊键） | 纸砚将其合并在 `keyMap` 三元组的第三段 | ⚠️ 必须**内置于方案自身**，不得写成共享函数（规避 shuangpin-practice 的 `initialsOfKey()` 抽象泄漏坑） |
| `meta` | 方案 ID、显示名、**`alphabet`（是否含 `;`）**、ü 归一策略、跨平台支持度、社区活跃度、是否可扩展形码、**数据来源出处（含 Rime schema 文件名 + commit hash）** | Rime 的 `schema_id` 命名约定 + 纸砚「PR 中说明方案来源」的要求 | ⭐ **「数据来源出处」应为必填字段**，且**必须精确到 commit hash**（本文档 §3.4 的取证方式即为范式：`rime/rime-double-pinyin@01a1328 / double_pinyin_flypy.schema.yaml L55-L84`），便于后续核对与合规追溯 |
| `calibration` | 该方案的**探针字校准集**（如小鹤：位/卷/云/爱/昂 + 拼/平/亮/料/来/老/楼） | S2 + S5 的校准样字建议（竞品均未产品化）；⭐ 已由 §4.2.2 十组探针升级为 A 级 | ⭐ 原创补充：用于 §6.3 的「输入法一致性校准」引导流程 |

**⭐ 五条硬性设计要求（来自竞品踩坑教训 + 本轮取证）**：

1. **方案文件必须完全自包含**。任何方案特有逻辑（如微软的 `;` 键、小鹤的零声母双口径、微软的 ü→Y）都必须在该方案自己的配置内表达，**不得写进共享层**。判定标准：新增一个方案时，**只需新增一个文件 + 一行注册**，不修改任何现有文件。

2. **`keyMap` 必须支持「一键多韵母」与「同键承载声母+韵母」两种情形**，且判定引擎**按位置解释**（第一键位 = 声母语义，第二键位 = 韵母语义）。这是 V/I/U 三键的设计本质（§2.1）。纸砚用 `"t/ue,ve/t"` 表达一键多韵母的思路正确，但字符串格式需结构化。

3. **⭐ `keyMap` 与 `zeroMap` 的值类型统一为 `string[]`，首元素 = 主键位/主口径**（取证强制要求，见 §5.2.2）。理由：官方 Rime 用 `derive` 表达「多合法编码」、用 `xform` 表达「唯一编码」，**两种语义必须能在同一数据结构中共存**。C-4（小鹤零声母 α/β）、C-6（微软 üe T/V）、C-12（微软零声母多值）三个问题由这一条统一解决，**无需任何方案特例**。这一条是本方案层设计中**相对全部四个竞品的原创增量**（纸砚/Shuang/shuangpin-practice 都是单值），因为竞品都没有做跨输入法环境兼容。

4. **⭐ `zeroMap` 的双口径兼容必须限定在「双字母零声母音节」子集**（取证收敛，见 §5.3 第 4 层测试族 4-A/4-B）。单/三字母零声母音节（`a`/`o`/`e`/`ang`/`eng`/`er`）在官方 schema 中是 `xform` 强制变形、**唯一编码**，若也做兼容判定就是把 bug 写进配置。

5. **贡献流程对齐纸砚的低门槛 + monkeytype 的可追溯**：① 单文件新增方案；② PR 模板**强制要求填写「数据来源出处（含 commit hash）」**（纸砚的做法，合规必需）；③ 参照 monkeytype 的 `CONTRIBUTING_BASIC.md` 模式，让**不需要本地开发环境**的贡献者也能通过 GitHub Web 界面提交方案（键位表是纯数据，无需构建）；④ ⭐ **新增：PR 必须附带该方案的推演验证结果**（用 §5.3 第 4 层测试族跑通，或按 §4.2.1 的模拟器方法给出探针音节编码表），**不接受「肉眼核对键位图」的方案贡献**。


### 6.3 方案差异对照功能的必要性（竞品空白点）

**目前没有任何竞品做「方案间键位差异高亮/对照」**（Shuang 支持 20+ 方案但无对照；ulpb 有独立的方案对比页但只是营销文案式的优劣论述，非键位级 diff；`shuangpin-practice` 只有一种方案；纸砚支持多方案与本地自定义方案但也无 diff 视图）。

**但方案迁移是真实行为**（V2EX 一手案例：用户学完小鹤两周后花一周切到微软）。因此建议提供：
- **键位级 diff 视图**：切换方案时，高亮显示「与上一方案不同的键」，并用 §4.3 的 8 组高频易错韵母对照 + §4.2 的探针字（女/绿/局/平）做快速校准题
- **迁移模式**：允许用户在过渡期同时接受两个方案的编码（类似 §3.2 的双口径机制，但跨方案），并统计「旧方案依赖率」逐步收紧
- **选型引导**：按 §4.7 的元信息（跨平台支持度/社区资源/形码可扩展性）给用户推荐

**⚠️ 必须同时明示**：巧手排查文的结论是「**练习工具与系统输入法方案必须一致，不可以混用方案练习**」。因此「迁移模式」需明确标注为**过渡期临时功能**，并提示用户尽快同步切换系统输入法。

## 八、本文档的核心结论（✅ 2026-10-17 一手取证后重写，8 条）

1. **小鹤双拼的 26 键声母/韵母主映射已达 A 级置信度，可直接实施**。本轮**取证升级**：不再只是「三信源交叉」，而是**三信源 + Rime 官方 `double_pinyin_flypy.schema.yaml@01a1328` v0.18 的 algebra 行级原文 + 31 探针音节推演矩阵**三重锁定。初稿遗留的 `er`（C-1）、`ün`（C-2）两项 P0 阻塞**已全部关闭**。**同时本轮排除一个低质信源污染**：21xqjy.com 两篇教程键位表大面积错误，若误采信会导致用户练错十余个高频韵母。

2. **C-4 的重大信源冲突已由官方定论：不是「α 对还是 β 对」，而是「官方两者都接受」**。小鹤官方文档 + ulpb + shuangpin.xyz + 纸砚四信源支持 α（爱=AI），初稿怀疑 Rime 指向 β（爱=AD）。**取证真相**：官方 flypy L57 对**双字母零声母音节用 `derive`**（保留 α + 派生 β，两者并存），L58 对**单/三字母音节用 `xform`**（唯一编码）。**我方「双口径兼容 + α 为主口径」策略与权威实现完全一致**，且兼容范围被精确收敛到 6 个双字母音节（`ai`/`ei`/`ao`/`ou`/`an`/`en`），其余零声母必须严格单值判定。

3. **判定引擎结论：采用「声明式 `{keyMap, zeroMap}` 映射表为唯一事实源 + 构建期生成 405 音节静态查表」的组合方案**，运行期 O(1)、无正则回溯、可全量单测；Rime algebra 与小鹤官方码表**仅作开发期交叉验证，不进产物**。必须建立**四层**质量验证体系（单测 / 交叉验证 / 端到端 / **多合法编码集合语义测试**）。

4. **⭐ 本轮最重要的架构增量：`keyMap` 与 `zeroMap` 的值类型统一为 `string[]`，首元素 = 主键位/主口径**。取证发现三个独立问题（C-4 小鹤零声母 α/β、C-6 微软 üe 的 T/V、C-12 微软零声母多值）**本质是同一件事**——官方 Rime 用 `derive` 表达「一个音节有多个合法编码」。因此**一个数组语义统一解决三个问题，无需任何方案特例**。计分口径：命中数组内任一编码即判正确，命中非首元素额外计「兼容键位」轻提示（不扣分、结算页汇总）。

5. **`{keyMap, zeroMap}` 格式的出处是纸砚（`Yidadaa/shuangpin`，507★），但该项目为 MIT + Anti-996 双许可，与我方 GPL-3.0 不兼容，代码与数据一律不得复制**，只借鉴格式思想。我方三处修正：① `keyMap` 改用结构化表达（弃用斜杠字符串）；② **`keyMap`/`zeroMap` 值改为数组以支持多口径**（结论 4，四个竞品都是单值，这是原创增量）；③ **新增 `zeroMode` 字段**（取证发现零声母只有「首字母重复」与「O 前缀补齐」两个家族，见结论 6）。

6. **⭐ 取证新发现（初稿未覆盖）：六大官方方案的零声母规则只有两种家族，且与是否用分号键相关**——**首字母重复家族**（小鹤、自然码，`alphabet` 无分号）与 **O 前缀补齐家族**（微软、智能ABC、四通、拼音加加，微软/四通 `alphabet` 含分号）。**产品收益**：`zeroMode` 让新增方案无需手写 12 条零声母映射，只选范式 + 极少数例外，**扩展成本从「N 种方案」降到「2 种范式」**。取证还确认 Rime 官方**只收录六个方案、不含搜狗**（C-7 取证难度因此更高），并发现四通雙拼有「实体键帽刻印」的独特属性（可作差异化内容选题）。

7. **多方案接口的五条硬性要求**：① 方案文件完全自包含（规避 shuangpin-practice 的 `initialsOfKey()` 抽象泄漏坑）；② `keyMap` 支持一键多韵母与「同键承载声母+韵母」，判定按位置解释；③ **`keyMap`/`zeroMap` 值必须是数组**（结论 4）；④ **双口径兼容必须限定在双字母零声母子集**（结论 2 的收敛，防「过度兼容」把两个音节合并）；⑤ 贡献流程对齐纸砚低门槛（单文件 + 单步 PR）+ **强制填写数据来源出处（含 commit hash）+ 附推演验证结果**（不接受肉眼核对键位图的贡献）。

8. **「方案间键位差异对照 / 迁移模式 / 输入法一致性校准」是四个竞品全部空白的功能点**，而方案迁移是真实用户行为（V2EX 一手案例）。**本轮已把 §4.2.2 的十组探针字升级为 A 级校准题库**（女/努、绿/路、军/云、平/拼、爱/昂、二/儿、双/亮、料/老、位/归、学/卷），可直接做成「5 分钟输入法校准」引导流程，打击「练习工具与系统输入法不一致」这一第一大故障源。此外，**我方走 `KeyboardEvent.code` 物理键位捕获架构，恰好规避了微软/四通双拼分号键在网页/远程桌面/快捷键软件中被拦截的工程风险**（S5 明确指出该风险；取证证实用分号键的方案比初稿估计的更多，此架构收益覆盖面更大）。

# md/ — Spec 提交目录说明

本目录（`./md`）是项目所有 **Spec（规格说明书）** 的统一提交与管理目录。
所有需求、模块设计、功能说明均以 **文件夹为单位** 进行提交，施工方（开发人员或 AI Agent）必须以 Spec 为唯一施工依据。

**全流程分为两个独立阶段，不可合并：**

```
需求提出 ──▶ ① 编写阶段：产出 spec-yyyyMMdd-vx 文件夹（xxx.md + schedule.md）
                        │  ← 交付即完成，到此为止，停下等指令
                        ▼
            （需求提出方下达开工指令）
                        │
                        ▼
            ② 施工阶段：按 Spec 施工 + 实时更新 schedule.md
                        │
                        ▼
            全部 [x] ──▶ 文件夹追加 (√) 归档
```

| 阶段 | 产出 | 是否写代码 | 是否可自行进入下一阶段 |
| --- | --- | --- | --- |
| ① 编写阶段 | `spec-yyyyMMdd-vx/` + `xxx.md` + `schedule.md` | **否** | **否**，必须等待开工指令 |
| ② 施工阶段 | 功能代码 + 更新后的 `schedule.md` | 是 | 全部 `[x]` 后归档 `(√)` |

---

## 1. 目录结构总览

```
md/
├── README.md                  # 本说明文件
├── spec/                      # 初始 Spec（基线，只读，不加日期后缀）
│   ├── 00-README.md
│   ├── 01-产品规格说明书.md
│   ├── ...
│   └── A3-技术验证Spike清单.md
├── spec-20261017-v1/          # 后续提交的 Spec（示例：未完成）
│   ├── 统计模块.md
│   ├── 打卡模块.md
│   └── schedule.md
└── spec-20261017-v2(√)/       # 后续提交的 Spec（示例：已全部完成）
    ├── xxx模块.md
    └── schedule.md
```

- **`spec/`**：初始 Spec，是整个项目的基线文档。**只读**，后续任何变更不得直接修改此目录，只能通过提交新的 `spec-yyyyMMdd-vx` 进行增量覆盖或补充。
- **`spec-yyyyMMdd-vx/`**：初始 Spec 之后提交的所有 Spec，一律使用此命名格式（详见下文）。

---

## 2. Spec 文件夹命名规则

格式：`spec-yyyyMMdd-vx`

| 片段 | 含义 | 说明 |
| --- | --- | --- |
| `spec` | 固定前缀 | 不可省略 |
| `yyyyMMdd` | 提交日期 | 动态取当天日期，如 `20261017` |
| `vx` | 当天批次号 | `x` 从 1 开始递增：同一天提交的第 1 批为 `v1`，第 2 批为 `v2`，以此类推 |

规则补充：

1. 批次号 **每天从 v1 重新开始计数**，跨天不累计。
2. 新建文件夹前，先检查当天是否已有同日期目录，避免批次号冲突；若 `spec-20261017-v1` 已存在，则新提交为 `spec-20261017-v2`。
3. 文件夹名中除规定的 `(√)` 完成标记外，**不得添加任何其他后缀、空格或特殊字符**。
4. 一个文件夹 = 一次完整提交，提交后内容即冻结语义（允许修错别字，不允许改需求）；需求变更请提交新批次 Spec，并在新 Spec 中注明「取代/修订 spec-yyyyMMdd-vx 中的某部分」。

## 3. Spec 文件夹内容要求

每个 `spec-yyyyMMdd-vx/` 文件夹内必须包含：

### 3.1 模块/功能说明文档（多个 `xxx.md`）

- 按 **模块** 或 **功能** 拆分，一个模块一个文件，如 `统计模块.md`、`打卡模块.md`。
- `xxx` 为模块/功能的基本说明名称，使用中文，见名知义，禁止使用 `1.md`、`new.md`、`未命名.md` 之类的无意义命名。
- 每份文档建议包含以下小节（可按需增减，但前三项必有）：
  1. **背景与目标** —— 为什么做、做成什么样算成功
  2. **功能需求** —— 逐条列出，可编号（如 `REQ-01`），便于 schedule.md 引用
  3. **交互 / UI 说明** —— 页面、组件、状态、边界情况
  4. **数据与接口** —— 涉及的数据结构、存储、API 约定
  5. **验收标准** —— 怎样算做完（尽量可测试、可勾选）
  6. **与既有 Spec 的关系** —— 是否覆盖/修订初始 Spec 或此前批次的某部分；若与基线冲突，须按第 4 节要求记录裁定

### 3.2 任务实施清单（`schedule.md`，每文件夹有且仅有一个）

`schedule.md` 是施工方的 **强制执行清单**，要求：

- 使用 Markdown 复选框罗列全部任务，任务需与模块文档中的需求条目对应；
- 每个任务标注：状态、负责人（可选）、完成日期（可选）；
- 状态标记约定：
  - `[ ]` 未开始
  - `[~]` 进行中（可在任务后备注进度说明）
  - `[x]` 已完成
  - `[!]` 阻塞（必须备注阻塞原因）
- 文末维护一个「更新记录」小节，每次更新清单状态时追加一行（日期 + 变更摘要）。

`schedule.md` 参考模板：

```markdown
# schedule — spec-yyyyMMdd-vx 任务实施清单

> 施工方必须按本清单逐项实施并实时更新状态；全部任务 `[x]` 后方可标记文件夹完成。

## 任务清单

- [ ] 1. 统计模块：xxx 功能（对应 统计模块.md REQ-01）
- [ ] 2. 统计模块：yyy 功能（对应 统计模块.md REQ-02）
- [ ] 3. 打卡模块：zzz 功能（对应 打卡模块.md REQ-01）
- [ ] 4. 联调与自测

## 更新记录

| 日期 | 变更摘要 | 更新人 |
| --- | --- | --- |
| yyyy-MM-dd | 初始化清单 | xxx |
```

## 4. Spec 编写阶段：基线参考、冲突裁定与交付边界

1. **基线先查后写**：在需求定义与 Spec 编写阶段，编写者应先检索 `./spec` 初始 Spec 中与本次需求相关的基线内容（产品定位、指标体系、数据模型、模块架构、交互约定等），作为本次 Spec 的参考依据，避免与既有设计脱节或重复造轮子。
2. **冲突以本次需求为准**：当基线 Spec 的描述与 **本次需求提出方** 的需求发生冲突时，**一律以本次需求为准**。基线仅有参考效力，不具优先权；**未发生冲突的部分，基线仍然有效并继续适用**。
3. **冲突必须显式记录**：凡出现上述冲突，须在本次 Spec 模块文档的「与既有 Spec 的关系」小节写明三件事：① 冲突点；② 基线原文出处（文件名 + 章节）；③ 「以本次需求为准」的裁定结论。同时在 `schedule.md` 对应任务条目后标注「⚠ 与基线冲突，以本批次为准」。
4. **基线只读不变**：冲突裁定只改变本次 Spec 的写法，**不得回头修改 `./spec` 基线文档去"对齐"**；基线的修订同样只能通过提交新批次 Spec 来表达。
5. **引用优于复制**：基线中仍有效的内容，建议以「参见 `spec/xx-xxx.md` 第 x 节」的形式引用，不整段复制，避免同一约定出现多处副本、后续演进时不一致。
6. **查不到基线不阻塞**：若本次需求在 `./spec` 中检索不到任何相关基线（全新模块/全新能力），直接在文档中注明「无相关基线，本批次为首次定义」即可，不得因缺少基线而搁置编写。

### 4.1 编写阶段的交付边界（硬约束）

7. **只写文档，不实现需求**：编写阶段的产出 **仅限文档**。Spec 写完后 **不得直接开始实现** —— 不写功能代码、不改配置、不建组件、不建表、不加依赖、不跑构建。即使需求看似简单、技术路线已经清楚，也一律不得"顺手先做掉"。
8. **交付物即需求定义任务的完成标志**：完成以下交付物后，**需求定义任务即告完成**：
   - `spec-yyyyMMdd-vx/` 文件夹已建立，内含全部模块/功能说明 `xxx.md` 与 `schedule.md`（清单初始状态为 **全部 `[ ]` 未开始**）；
   - 向需求提出方同步：本次批次包含哪些模块、与基线的冲突裁定情况、仍需对方拍板的待确认项。
9. **交付后停下，等候下一步指示**：交付完成后必须停止动作，**等待需求提出方的明确开工指令**（如「开始施工 spec-20261017-v1」「按 schedule 先做第 1~3 项」）后，才可进入第 5 节的施工阶段。不得自行开工、不得预判意图先做一部分、不得把未经确认的推测性改动预先落进代码。
   - *例外*：若需求提出方在**同一条指令中已明确要求「写完直接实现」/「文档与实现一起交付」**，视为已下达开工指令，可连续执行。

> 说明：本节的裁定发生在 **编写阶段**（基线 vs 本次需求），结论会固化进 Spec 文档；进入第 5 节的施工阶段后，施工方看到的已是唯一确定的 Spec，无需再做裁定。**编写与施工是两个独立阶段，编写完成不自动触发施工。**

## 5. 施工方（读取 Spec 的人员/Agent）强制约定

> **进入前提**：需求提出方已明确下达开工指令。按第 4.1 节，编写阶段交付 Spec 后不得自动转入施工。

1. **先读 Spec，后动代码**：施工前必须完整读取该批次文件夹内所有 `.md` 文档，以及 `spec/` 初始 Spec 中被引用的相关章节。
2. **无指令不施工**：未收到明确开工指令前，**不得改动任何源码/配置**；不得以"顺手优化""预研一下""先把地基打好"为由提前动工。
3. **严格按 Spec 施工**：不得擅自增删需求、改变交互或数据约定；发现 Spec 有误或不可行时，**停下来向 Spec 提交人反馈**，而不是自行发挥。
4. **实时更新 `schedule.md`**：每完成一项任务立即勾选 `[x]` 并补充完成日期；遇到阻塞标记 `[!]` 并写明原因。禁止批量补记或事后一次性更新。
5. **冲突处理**：若新批次 Spec 与初始 Spec 或历史批次冲突，**以最新批次为准**，并在新 Spec 文档中显式写明取代关系；已按第 4 节标注「以本次需求为准」的条目，施工方直接按该裁定执行，不再质疑基线。

## 6. 完成标记规则 `(√)`

当且仅当某批次 `schedule.md` 中 **所有任务均为 `[x]`**（无 `[ ]`、`[~]`、`[!]` 残留）时：

- 将文件夹重命名，在原名称末尾追加 `(√)`：

  ```
  spec-yyyyMMdd-vx  →  spec-yyyyMMdd-vx(√)
  ```

- 示例：`spec-20261017-v1` 全部完成后重命名为 `spec-20261017-v1(√)`。

补充约束：

1. `(√)` 中的对勾为 **全角字符 `√`**，括号为半角 `()`，请原样复制，勿用 `(✓)`、`(done)`、`(完成)` 等变体，便于统一检索。
2. 已标记 `(√)` 的文件夹视为 **归档基线，只读**：不得再修改其中任何文档，也不得移除标记；后续修订一律通过提交新批次 Spec 完成。
3. 标记 `(√)` 的同时，应在 `schedule.md` 的「更新记录」中追加一行「全部任务完成，归档」。

---

## 7. 其他通用约束

1. **编码与格式**：所有 `.md` 文件使用 UTF-8 编码、标准 Markdown 语法；文件名使用中文或英文均可，但同一批次内风格保持一致。
2. **禁止提交代码**：本目录只存放 Spec 文档，不得放入源码、构建产物或二进制大文件；示意图请使用 Mermaid 或外链图片。
3. **一事一批**：一个批次聚焦一个主题/一轮迭代，避免把互不相关的大量模块塞进同一个文件夹；内容过多时拆分为同日期的多个批次（v1、v2…）。
4. **提交即通知**：新建 Spec 文件夹后，应同步告知施工方（或在协作渠道中登记），避免 Spec 提交了却无人施工。
5. **检索约定**：查找未完成批次用 `spec-*` 排除 `(√)`；查找已归档批次用 `*(√)` 结尾匹配。

## 8. 快速对照示例

以 2026-10-17 提交第一批 Spec 为例：

```
md/
└── spec-20261017-v1/          # 当天第 1 批
    ├── 统计模块.md             # 模块说明文档
    ├── 打卡模块.md             # 模块说明文档
    └── schedule.md            # 任务实施清单（施工方实时更新）
```

施工完成后：

```
md/
└── spec-20261017-v1(√)/       # 全部任务 [x]，归档只读
    ├── 统计模块.md
    ├── 打卡模块.md
    └── schedule.md
```

同一天再提交第二批，则命名为 `spec-20261017-v2/`，规则同上。
